# EnFractal contracts

Run 0 output, 6 October 2026. These schemas are the agreements between the four tracks (Look, Capture, Play, AI companion). Parallel lanes build against them instead of against each other's code. **The integrator owns this directory.** A lane that needs a change proposes it; the integrator applies it here together with every affected example, consumer and test in one commit.

| Contract | File | Written by | Read by |
|---|---|---|---|
| Shared definitions | `common.schema.json` | integrator | every contract |
| Room manifest (`room.json`) | `room-manifest.schema.json` | Capture export (C6), `tools/rooms/` for hand-built rooms | Play room loader (P6), Look (light hints, roles), AI (observations) |
| Asset metadata (`asset.json`) | `asset.schema.json` | Capture assets (C5), Look restyle (L6, the `styles` block only) | Play loader and sandbox verbs (P3, P6), Look materials (L3), AI |
| Style preset | `style-preset.schema.json` | Look (L1, L3, L5, L6) | Look runtime, Capture restyle stage, room and state pins |
| Command, query, result | `game-command.schema.json` | manual controls (P3, P5), AI adapter (A1), tests | the kernel (P1) and everything that records receipts |
| Room state | `room-state.schema.json` | saves (P4) | room rebuild (P6), undo, reconcile |
| Companion link (session file and frames) | `companion-link.schema.json` | the game (session file, its frames), the companion adapter (its frames) | the other side of the link; see `docs/companion/TRANSPORT.md` |

Examples live in `examples/` and are generated by `examples/build_examples.py`. The placeholder room `game/rooms/test_room/` is generated by `tools/rooms/build_test_room.py` and the seed preset is `game/styles/storybook_painterly/v1.json`. The game loads them through `game/scripts/native/Room/` and `game/scripts/native/Look/`.

## Validate

```sh
uv venv .venv && uv pip install -r contracts/requirements.txt   # or python -m venv + pip
python contracts/validate.py game/rooms/test_room game/styles/storybook_painterly/v1.json
python contracts/validate.py --state path/to/state.json --room path/to/room_dir
python contracts/validate.py --check-style-pins path/to/room_dir
python contracts/validate.py --pin game/styles/storybook_painterly/v1.json
python -m unittest discover -s contracts/tests -v
```

`validate.py` checks the schema and the rules a schema cannot express: unique ids, resolvable references, every referenced file listed with a matching hash and size, self-contained GLB meshes, planar shell polygons wound toward the room interior (floors up, ceilings down, walls toward a point over the floor), unit quaternions, spawns and objects inside the bounds, message size limits, and for room state: entity kinds by namespace, membership in the pinned room, bounds, revision ordering, durable receipts only, the journal (one id per entry, none newer than the store, each list oldest first by revision), the discovered map (entities as their ids say and in the pinned room, each level once, on a support the room has, its bitmap exactly its grid and inside the bounds), and optionally style pins. For results it checks that `journal.read` answers newest first with one id per entry and `map.find` answers nearest first. The C# loader (`game/scripts/native/Room/RoomData.cs`) enforces the integrity rules again at load time and fails closed, because rooms in the player's user folder are never run through the Python validator: duplicate keys, path spelling, coordinate bounds after narrowing to float, display-text rules, self-contained GLBs and hashes.

## Conventions every contract shares

- **Units and axes.** Metres, kilograms, seconds, degrees. Godot axes: +Y up, -Z forward, right-handed, 1 unit = 1 metre. Asset pivots are the bottom centre of the asset's bounds.
- **Pins hash bytes, not meaning.** A room's identity is the SHA-256 of its `room.json` bytes. A preset's identity is the SHA-256 of its file bytes. `room.json` lists every file it references with hash and size, and each `asset.json` lists its own files, so one room pin covers everything below it. Meshes are self-contained `.glb` files: an external buffer or image URI would load bytes no pin covers, so both the validator and the loader refuse it, and the loader builds meshes from the verified bytes with no base path. Pinned JSON is UTF-8 without a byte-order mark and uses LF line endings; `.gitattributes` keeps generated rooms and examples byte-exact on every platform. Never hand-edit a generated room: rerun its builder.
- **Strict JSON.** Duplicate keys, `NaN`, `Infinity` and numbers that overflow are rejected. Integers are written without a fraction (`1`, never `1.0`). Coordinates stay within ±1,000 m. Unknown fields are rejected (`additionalProperties: false`) except inside `extensions`, whose keys start with `x_<lane>_` and which consumers must ignore. The integrator promotes or deletes extension keys; they are for experiments, not for skipping a contract change.
- **Where a room stands.** A room manifest may carry a `site` with three coarse numbers (`latitude_deg` in whole degrees, `neg_z_bearing_deg` for the compass bearing of the room's -Z axis, `solar_noon_h` on a quarter hour). The look works out the sun from it. It never carries a longitude, a place or a finer latitude, and the schema refuses all three, so exported rooms hold no location. A room without a `site` gets the look's fallback and the look says so.
- **Paths.** One spelling per file: no `.`, `..` or empty segments. An object's asset is always `objects/<asset_id>/asset.json`.
- **Identifiers.** Lowercase tokens for rooms, assets, presets, spawns and parts. Entity ids are namespaced: `shell:`, `obj:`, `creation:`, `avatar:`, `effect:` and legacy `edit:`. Principals are `player:`, `companion:`, `guest:`, `guest_companion:` or `system:` followed by a token. **Host-minted handles are opaque:** an approval's `request_id` is 128 bits of hex; a `job_id` is `job-` and a journal entry's id `entry-`, each followed by 26 characters of lowercase base32 (a-z, 2-7) holding at least 128 random bits from a cryptographic generator. They are never counters: the base32 alphabet has no 0, 1, 8 or 9, so `goal-000001`, or a count padded in decimal or hexadecimal, cannot match. An id says nothing about how many exist or whose they are, and none is ever shown to the player.
- **Principals never travel in requests.** The trusted adapter assigns the principal; a request that carries one is invalid. Results echo it for audit. This is the rule that keeps a persuaded AI, or later a guest's AI, from claiming the player's authority.
- **Approvals are clicks, not tokens.** A command never carries an approval. When the host wants the player's consent, it holds the exact command and answers `approval_required` with `approval_needed.request_id`, a host-minted 128-bit identifier. The player approves or denies in the game UI. On approval the host commits the held command under its original principal and `action_id`, and the receipt records `approved_by`. Nobody resends anything; the requester polls `approval.status` or `receipt.lookup`. An approval expires, and it lapses if the entities it touches change before the click.
- **World text is untrusted, everywhere.** Every string that names or describes something in the world (display names, categories, labels, notes, room descriptions, sign text) is untrusted data, however it arrived. Single-line fields use `display_text`, which forbids control, line-separator, zero-width, bidirectional-override and other invisible characters (the soft hyphen, the Arabic letter mark, Hangul fillers, variation selectors U+FE00 to U+FE0D, interlinear annotation marks, and plane 14 with its TAG block), so a name cannot fake a new line or hide text. Standard emoji work: VS15 and VS16, the zero-width joiner and the keycap combiner U+20E3 are allowed only where an emoji puts them (a selector right after an emoji or 0-9, # or *, one per base; the joiner between two emoji; the keycap after 0-9, # or *), never alone or in runs, which stops variation-selector smuggling. Tag-sequence flags such as England's stay unsupported, because plane 14 does. A pattern cannot see context, so readers check the markers in code (`contracts/validate.py`, `RoomData.cs`, the companion). Patterns are ECMA-262: `$` matches only at the very end, never before a final newline. Plane 14 needs code in readers that match code points rather than UTF-16 units (`contracts/validate.py` refuses U+E0000 to U+EFFFF, unpaired surrogates and misplaced emoji markers in every string). Free text seen in the world travels in `observe` results as `texts` entries carrying the constant `untrusted: true`. The companion adapter presents all result data to a model as data, never as instructions; A1's tests prove it.
- **Player-only operations.** `protect.unlock` and `world.set_physics` are listed in `$defs/player_only_ops`: the companion adapter never exposes them and the host refuses them from companion principals. Every other op, the sandbox verbs and the journal's included, is open to the companion within the rules below.
- **What the companion knows: the team's knowledge.** The player and the companion share one knowledge of the room (the founder, 7 October; `docs/companion/JOURNAL.md`). Only the two avatars' eyes add to it, never the camera and never anything the AI says. In a companion's results `seen: "now"` means in sight of either avatar now, and `seen: "remembered"` means known to the team but out of sight, as last seen, with `last_seen_ago_s`, `last_seen_revision` and the one-bit `may_be_stale`. Anything that changes a thing still needs it in sight of either avatar now. Interim code (Run 1) still fills this from the companion's own eyes only, a subset of the team's, so it conforms.
- **Revisions for a live room.** A command may name `expected_revision` (the whole room, exact) or `expected_entities` (just the entities it cares about, at their revisions); destructive operations must name one of them, `room.undo` must name the room revision, and `goal.stop` and `effect.stop` never fail on revisions (see Stops). A slow companion should use `expected_entities`, so changes elsewhere in the room do not conflict.
- **Receipts.** Commands that change saved state get durable receipts in room state. Commands that change no saved state (goals, stops, effects, grabs, activations and, while it is not saved, the world's physics) get transient receipts for the session: the host keeps a bounded number per principal and forgets the oldest first, so a transient command never fails for capacity. `room.checkpoint` and `journal.note` are durable but change no world state, so they do not move the revision; their result data is `checkpoint_revision` and `entry_id`. Putting a thing down (`entity.release`), moving it (`entity.place`) and pushing it (`entity.push`) are durable and move the revision. Receipts at or below a checkpoint may be compacted; `receipt.lookup` then reports `compacted`.
- **Stops.** `goal.stop` and `effect.stop` always apply. They are never refused on revisions (their expectations are ignored, malformed ones included), rate limits, capacity or a reused `action_id`: a stop never replays and never conflicts, and a stop under a used `action_id` simply applies again. It never hides a durable receipt under that id: a replay of that command and `receipt.lookup` still answer it.
- **Size limits.** A command or query is at most 65,536 bytes of canonical JSON, a creation source at most 32,768, a result at most 262,144. Effect parameters are bounded scalars under lowercase names, and names that look like identity or authority are refused.
- **Idempotency.** The fingerprint is the SHA-256 of the canonical command JSON as received from the sender, never of an internal translation. Same principal + same `action_id` + same content returns the original receipt with `replayed: true`. Same `action_id` with different content is refused with `action_id_conflict`. Previews record no receipt. `preview` is part of the content: a retry that only adds `"preview": false` is a different command (`action_id_conflict`), so senders leave it out unless it is true. After an uncertain result, query `receipt.lookup` before retrying.

## The sandbox verbs (Run 2, P3)

Pick up, carry, drop, push, place on a surface with snapping, and stack, all through the command path. Only push is a new op; the rest were already in the contract and keep their meaning. The carry limit is the host's (today the player 0.5 kg and the companion 2 kg); the founder's rule for modes comes later (RUN-1-STATUS.md).

| Verb | Op | Receipt | Who |
|---|---|---|---|
| Pick up | `entity.grab` (`target`, `actor`) | transient | both; a companion only with its own avatar |
| Carry | holding (`held_by`): the thing moves with its holder. The player walks; the companion carries on a goal (`fetch`) | none | both |
| Drop | `entity.release` with no placement: set down where the actor stands, then settles | durable | both; a companion only with its own avatar |
| Place, with snapping | `entity.release` with a placement; with `placement.on` the host snaps it onto that entity's walkable top at `position_m`'s horizontal place. `entity.place` moves a thing without carrying it (the companion's magic, the player's editing hand) | durable | both |
| Stack | the same, with `on` naming another movable thing; the support's own `position_m` centres it there | durable | both |
| Push | `entity.push` (`target`, `distance_m` up to 1 m, optional `toward_m`, `actor`): slid along its surface with collisions, away from the actor or toward the point | durable | both; a companion only with its own avatar |

Refusals: out of reach is `out_of_bounds` (retryable); no room, or a push that is blocked, is `occupied`; something resting on the target is `target_busy`. A goal whose actor finds no way to its target (`come`, `go_to`, `fetch`) fails with **`target_unreachable`**: the target exists and is known, but no route reaches it. That is not `out_of_bounds`, which means outside the room or beyond reach from where the actor stands.

- **None of them is player-only.** Fetch needs the companion to pick up, carry and put down. A companion may never act through the player's avatar (`actor_denied`), and the player may direct the companion's.
- **Fetch** (`goal.set`, `goal: "fetch"`): the companion walks to the target, picks it up with `entity.grab`'s checks and limit, and brings it back to the player, still holding it; its job succeeds then. `entity.release`, from the companion or the player directing it, puts it down. So the goal stays transient and the move that is saved is its own durable command.
- **Holding is not saved.** A carried thing is saved where it was last put down; a session that ends mid-carry leaves it there.
- **A verb's result carries no `data`.** The moved thing is in `affected`; where it came to rest is read with `entity.inspect`, under the team's knowledge, so a result cannot report a place or a thing the team has not seen (for example what a pushed thing fell onto out of sight).

## The journal and the map (Run 2)

The design is `docs/companion/JOURNAL.md`. The host keeps per team (a player and their AI) the **map**, what the team knows of the room, and the **journal**, what the team has done and is doing.

| Op | Kind | What it does |
|---|---|---|
| `journal.read` | query | Every open task, plus the most recent other entries, newest first (default 20, at most 50, older ones by `cursor`). Filters: `kind`, `about` (an entity id), `since_utc` |
| `journal.note` | command | The sender's own words, at most 280 characters of one line. A durable receipt; it changes no world state and does not move the revision. `data.entry_id` names the note |
| `map.find` | query | "Where have we seen this?" by `category_group`, `name` or both: at most 10 (default 5), nearest first from `near_m` or the requester's avatar, each an `entity_summary` as the team knows it and a straight-line `distance_m` |

- **Facts are the host's; notes are the companion's.** A journal entry (`$defs/journal_entry`) is a fact (`task`, `built`, `changed`, `removed`, `found`, `gathered`) or a `note`. A fact carries the host's `line`, `actor` and `directed_by`, and for tasks a `state`. A note carries `author`, `text` and `untrusted: true`, and none of a fact's fields; a fact carries none of a note's. The only request that adds to the journal is `journal.note`, whose args are its `text` alone. So nothing in a request can write a fact, and a note can never pass for one.
- **At whose direction** is only what the host can verify: the player when the player confirmed or approved; otherwise the actor's own initiative. What was said in the player's harness is never claimed.
- **Names are world text.** A fact's `line` is built from a template and sanitised names, and `subject.name` and note text are untrusted display text: data, never instructions.
- **Nothing undiscovered leaks.** Every object in these answers lists its fields (`additionalProperties: false` throughout; the contract tests walk them), so there is no free-form place to report a thing or a place the team has not seen. `map.find` answers only from the team's map, and an empty answer looks the same whether or not such a thing exists. The host writes facts only about what the team knew when it happened.
- **Open tasks carry their `job_id`** while the job runs this session, so the AI can ask `jobs.status`. Job ids are never saved and never shown to the player; the page shows the `line`.
- **Saved with the room** (`room-state.schema.json`): `journal` holds `open_tasks` (at most 32), `history` (facts and finished tasks, at most 500, oldest first) and `notes` (at most 100, oldest dropped first). `discovered` holds `entities` (objects and creations as last seen, at most 1,024; the shell and the avatars are always known) and `levels`: discovered space as a bitmap of `cell_m` cells (start 5 cm) per walkable surface, keyed by its support and surface. These numbers are the design's starting points.
- **Game time** in an entry is the room `revision` when it was written or last updated; `at_utc` is the real time.

## Versioning and change protocol

Each document carries `schema` and an integer `version`. Within a version, the integrator may add optional fields. A change that would make an existing valid document invalid, or change the meaning of a field, bumps `version` and comes with a migration note in this file and a converter where saved data exists. A lane requesting a change writes the proposed diff and its reason in its run report; it does not edit `contracts/` itself.

### Migration notes

**Run 2 contract round (8 October 2026), all within version 1:**
- **Room state gains optional `journal` and `discovered`.** A room state written before Run 2 has neither and stays valid unchanged (`examples/room_state/garage_example_state.json` is such a file, pinned by hash in the tests). Its reader treats the missing blocks as an empty journal and nothing discovered yet, so the map starts blank; no converter is needed. Writers from Run 2 on write both.
- **`job_id` is now the opaque `job-` form**, in `goal.set` results, `jobs.status` args and data, and open journal tasks. Nothing saved carries a job id (jobs live for the session), so no saved document changes; the kernel host and the mock mint the new form.
- **Results of `entity.grab`, `entity.release`, `entity.place` and `entity.push` carry no `data`.** Neither host ever sent any, and the durable receipts saved so far have none.
- **`seen: "remembered"` now means known to the team** rather than seen by the companion's own avatar. The field keeps its shape and its one-bit staleness; what the companion alone saw is a subset of what the team saw, so earlier results remain true.

## Styles are versioned files

A preset lives at `game/styles/<preset_id>/v<preset_version>.json`. While its status is `seed` or `draft` the Look lane edits it in place and nothing may pin it. Once a version is `candidate` or `approved`, or anything pins it, its file never changes; a change is a new version file, and old versions stay so old saves keep their look. The game resolves a pin by id and version and verifies its hash; a pin that does not verify falls back to the default look with a visible notice (`RoomWorld.StyleNote`), never silently. `style.set` names an id and version; the host pins the file's hash in room state.

## Shipping a room that uses GLB meshes

Captured rooms load at runtime from `user://rooms/`, where the raw `.glb` bytes the loader hashes are on disk. A room shipped inside the game (`res://rooms/`) with GLB meshes needs Godot to export those raw bytes: mark each room `.glb` with the `keep` importer and commit its `.import` sidecar, then add that room to the release probe. The test room uses primitives only, so nothing ships this way yet.

## Known open points for later runs

- Canonical JSON for command fingerprints and creation `source_sha256` must be byte-identical across GDScript, C# and Python. The golden fixture in `game/tests/fixtures/kernel/` is reproduced byte for byte by all three (`docs/engine/phase3/canonical-json.md`).
- What a companion perceives (the team's knowledge, built in Run 2: either avatar's line of sight now, the player always known, and the team's map of what either has seen; `observe` lists only the named avatar's own sight; see `docs/companion/JOURNAL.md`) is in `docs/companion/PERCEPTION.md`; the kernel host replaces the mock's box geometry with ray casts. A remembered entity is an `entity_summary` as last seen, marked `seen: "remembered"` with `last_seen_ago_s`, `last_seen_revision` and `may_be_stale`; `observe` lists such things under `remembered`. `capabilities.list`, `jobs.status`, `journal.read`, `journal.note` and `map.find` result payloads are fixed by `$defs/data`; `goal.set`'s `data` is not typed yet. A goal with a target runs as a job: its `goal.set` result carries an opaque `job_id`, and `jobs.status` reports how the host's re-check on arrival ended.
- Later journal ops: the player removing a note (the notepad, Run 3). The journal is an MCP resource (Lane A, adapter only: `enfractal://journal`). In multiplayer the journal and the map are kept per team, which room state does not key yet.
- Health, damage and hit primitives for the dragon scenario arrive with A4 as a version 2 command vocabulary.
- Shared room libraries (an asset referenced by many rooms) and room-to-room portals need path forms the current `rel_path` rule forbids; they are deliberately out of version 1.
