# Phase 2 shared-authority adversarial fixture design

**Status: test design and data vectors only, 1 October 2026.** No shared authority server, account service, admission service, replication, persistence, or remote multiplayer is implemented by this document. This is a bounded handoff for [E09/E10](../../roadmap/BACKLOG.md) using the [proposed cross-system contract](../phase0/contract-v0.1.md) and the [local ENet+DTLS probe](transport-feasibility.md). The companion [data vectors](../../../tests/fixtures/phase2_authority_vectors.json) describe observable behavior; they are **not a frozen wire schema**.

## Smallest useful executable fixture

Run one headless Godot authority and two independent local client processes on `127.0.0.1`, with `ENetConnection` and DTLS. Generate an ephemeral certificate in test setup, give clients its public trust certificate and a fixed expected hostname, and require certificate/hostname validation before application admission. Bind the listener only to loopback; choose an OS-assigned port and never open the firewall. Use a per-run nonce and a bounded overall timeout so a stale report cannot pass.

A trusted test setup supplies two separate, one-use, short-lived **ticket labels** for Alice and Bob. The harness resolves these labels to random tickets and server-side records; the fixture JSON contains no usable credential. A ticket record binds principal, logical avatar, `world_id`, `frame_id`, admission epoch, expiry and reserved slot. This simulates the output of a future HTTPS account/admission service; it does **not** test that service or prove durable player identity. After a valid DTLS handshake, the server redeems a ticket once, binds the resulting application session to the actual encrypted connection handle, and sends only that connection its opaque session identifier. The server never accepts `principal_id`, `avatar_id`, `owner_id` or a connection identifier as authority when supplied in a packet.

Initialize an isolated synthetic flat, bounded test cell with a fixed 30 Hz authority tick, two avatars and a server-owned rules profile containing gravity, movement bounds and a modest ambient wind. The exact rule values, profile revision and tick duration are **fixture parameters**, not production constants. A client sends a small typed intention: move axes and glide on/off. The server validates session, world/frame/epoch, sequence, size, finite ranges and permission before applying it at a tick. The server computes position and glide/wind effects from its own rules and collision, then sends snapshots to both admitted clients. A second private field in the authority state provides a disclosure check: each client sees only the fields granted to it.

Use a small typed-packet adapter; do not deserialize Godot objects or expose arbitrary RPC method names. Keep input queues bounded. Record rejected packet category and counters without logging tickets, session values, prompts or private state. Both clients should compare snapshots by authoritative tick, avatar ID and server revision, rather than expecting simultaneous packet arrival. The fixed-step simulation can be a minimal kinematic seam for this proof; E07's terrain/contact physics and E13's permissioned effects must be integrated in later gates.

## Boundaries the harness must keep separate

1. **Server identity:** a valid certificate chain and expected hostname establish which endpoint the clients connected to. This precedes any ticket. An encrypted socket does not identify a player.
2. **Admission identity:** a ticket grants one admission to a specified world/avatar at the current epoch. It is a bearer credential, not parcel ownership. The server binds the admitted principal to the live connection; a copied session value on another connection cannot impersonate it.
3. **Authority:** a client proposes intention only. The server owns positions, applied wind/glide result, rules, permission decisions, tick/revision and snapshots. Claimed position, owner, force or rules fields fail closed; no state change follows.
4. **Transient sequence:** a repeated or stale movement `seq` in one application session/epoch is dropped. A rejected duplicate must not reapply movement. A new session starts a new sequence space and fences the old one.
5. **Durable action receipt:** `action_id` replay for committed building/edit commands is a different E15 problem. An identical committed retry must return its original receipt after authentication and fingerprint comparison; it must **not** be rejected merely because a transient movement sequence was used earlier. This fixture contains no durable edits and cannot pass the E15 idempotency/recovery gate.

## Acceptance observations for the narrow prototype

The [vectors](../../../tests/fixtures/phase2_authority_vectors.json) are ordered adversarial scenarios, not independent unit tests. Reset the authority and regenerate ephemeral credentials for each scenario unless `continue_from` explicitly names a prior state. For every rejected packet, compare the authoritative state hash or complete state snapshot immediately before and after the attempted operation **at the same tick**; ordinary time advancement must not be mistaken for a rejected effect. Also assert no private snapshot or session information was sent before admission. Record the reason category, not the credential.

The first pass should demonstrate: both separately authenticated clients join one cell; their valid intents change only their server-owned avatars; both observe the same authoritative result for a named tick; the glide/wind result comes from the pinned server rule revision; forged position/owner/rules/other-session values fail; duplicate/stale sequences do not apply twice; reconnect fences the old session; invalid identity or ticket cannot receive world snapshots; oversized, non-finite and unknown packets fail before simulation. Keep a summary with engine/template hashes, process count, interface/port, elapsed time, setup nonce, per-vector outcome, server revision and snapshot equality evidence. An independently rerunnable Windows loopback test is the first gate; a Windows client to Linux headless host test is still required before E09 acceptance.

The fixture should fail if the old connection can act after replacement, if a ticket is reusable, if a client supplied position/owner/rules value is reflected in state, if a duplicate sequence advances simulation for that avatar, or if a client can access another player's private field. Packet loss and snapshots need later measured tests; a single loopback agreement is no E10 replication pass.

## Explicitly deferred gates

The probe would still lack real account authentication, secure ticket issuance/storage and concurrent redemption, production certificate renewal/revocation policy, exported two-platform binaries, an Internet route, loss/jitter/reordering, bounded load, durable identity and reconnect across host restarts, crash-safe state/receipts, authoritative terrain/collision revision handoff, permissions on parcel/effects, portal fencing and incident logging review. Godot's current DTLS revocation/pinning limitation from the [transport feasibility report](transport-feasibility.md) remains relevant. None of the vectors should be reported as proof of public-service readiness or E09/E10 completion.
