# Phase 1 visual terrain streaming spike

The Barton Creek viewer now prepares one visual LOD tile at a time on a Godot worker. Its CPU job produces only packed vertex, normal, color, UV and index arrays. The main thread creates the `ArrayMesh` and replaces the visible `MeshInstance3D.mesh` after the job completes. The prior mesh stays visible until then. This isolates the expensive 2 m tile calculation without making the active scene tree or GPU upload a worker operation, in line with Godot's [thread-safe API guidance](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html).

The scheduler holds at most one in-flight job and 64 pending tile IDs. It rechecks the camera's desired LOD when a detail job finishes: a large jump makes that result stale, so it is discarded and the old mesh remains. A base tile is retained even after a jump, because complete coarse coverage is still needed. An in-flight calculation is not preempted; it finishes before the next tile starts. Every `WorkerThreadPool` task is joined, including during viewer shutdown, as required by [Godot's WorkerThreadPool contract](https://docs.godotengine.org/en/stable/classes/class_workerthreadpool.html). The map package is read-only while a job runs. No scene nodes, meshes or textures are created or changed in the worker.

All three LODs keep the same source-derived 2 m tile-edge heights. The existing seam test checks 2/8/32 m combinations and upward triangle winding. Fine, medium and coarse tiles contain 131,072, 9,464 and 1,592 triangles respectively. Collision remains on its separate, fixed-resolution path; a visual LOD swap cannot remove an active collider.

## Diagnostic measurements

Five fresh headless Godot 4.7.2 runs on the development laptop used one 512 m Barton Creek tile, forced one stale 2 m request, then built and committed one valid 2 m request. Worker dispatch took **0.04–0.05 ms**, the CPU build took **93.19–95.19 ms** off the main thread, and the main-thread mesh commit took **5.11–5.64 ms**. The previous synchronous fine-tile build took about **104–106 ms** on this machine in the same headless geometry test. These are local diagnostics, not warm gameplay frame percentiles or a low-device pass. The hidden-window renderer and target 8 GiB integrated-GPU machine still need route-based profiling.

A separate hidden-window greenbelt capture at 1280×720 on this laptop's RTX 2070 Super exited successfully with an empty LOD queue. Its last 8 m build took 29.96 ms off-thread and commit took 1.30 ms; 42 settled frames had a reported 6.94 ms median and p95. The camera was stationary, and hidden-window timing is not representative of a walking or high-speed travel route.

A fine tile's packed vertex/index arrays account for roughly **4.52 MiB**; the worker also uses a temporary height cache of roughly **0.26 MiB**. Those figures exclude Godot object overhead, upload copies, resident meshes, other map features and GPU allocation. The initial spike did not yet budget resident meshes.

Run the focused checks with `godot --headless --path game --script res://tests/terrain_seam_smoke.gd` and `godot --headless --path game --script res://tests/visual_streaming_smoke.gd`. The streaming test confirms that dispatch leaves the coarse tile visible, a stale result is discarded, a valid result is later committed, and the 2 m triangle count is intact. The existing map, movement, creation, world-state, world-physics and workshop integration headless tests also passed in this phase.

## Bounded residency and phased startup follow-up

The viewer now builds the 3×3 coarse tiles around its launch camera synchronously, then queues the remaining **55 coarse tiles** nearest first through the existing worker. A full-screen loading cover stays up until all 64 coarse meshes are committed, so a partially built landscape is never shown to the player. Loading-time input is consumed before the workshop's edit/save shortcuts, while its collision-bearing nodes remain active. A camera jump during loading reprioritizes the remaining base tiles; an already-running base result remains useful and is committed. Queue refreshes exclude that in-flight key, and detail work waits until the base phase is complete. The loading screen is a temporary presentation gate, not a claim that all map loading is asynchronous. Package validation, feature construction, the nine nearby tiles, and collision-ring creation remain synchronous.

Each tile retains its stitched 32 m base mesh. More detailed 8 m and 2 m meshes can be released by swapping the instance back to that base mesh without affecting terrain collision, which is sourced independently. The default resident terrain-mesh payload ceiling is **64 MiB**. The complete coarse base has an explicit floor of **5.70 MiB** for this map: requests below the floor are clamped, including changes made after loading, and lowering the cap immediately evicts detail as needed. Accounting measures the packed vertex, normal, color, UV and index byte counts for every retained base mesh plus every active detail mesh. It is an enforceable resource-payload proxy, not an observed GPU memory or total process-memory limit; driver buffers, temporary worker arrays, transient upload copies and non-terrain objects remain outside it. A prospective detail commit evicts farther detail first; if it cannot fit without displacing a nearer detailed tile, the result is rejected and held out of the queue until the camera, budget or residency state changes. Each frame still commits at most one worker result.

The `terrain_residency_smoke.gd` test deliberately jumps between opposite map corners while a base job is running, verifies near-first reprioritization and base-before-detail ordering, all 64 visible coarse meshes, a retained loading cover until completion, farther detail eviction, budget rejection, reloading an evicted 2 m tile, and below-floor budget changes both during and after startup. The `terrain_loading_input_smoke.gd` test sends the actual F5 save shortcut while the loading cover is visible and after it disappears; it confirms the save is blocked only during loading and source-grid walking collision remains available. Headless Godot 4.7.2 runs on the development laptop measured the initial 9 tiles at roughly **65–70 ms** and all coarse tiles complete after roughly **516–533 ms** of test elapsed time. The largest individual coarse mesh commit was about **0.33 ms**; a fine-detail commit was up to about **5.4 ms**. Base meshes account for **5.70 MiB** of packed payload and each fine mesh for **4.52 MiB**. A tightened-budget test forced detail evictions, a justified rejection and a successful reload. These headless timings are diagnostics, not rendered-frame percentiles; the synchronous nine-tile launch remains a meaningful hitch.

Run `run-engine-tests.ps1` for the full Godot suite, including seam, visual-streaming and residency checks. That must measure presented p95/p99 frames, upload stalls, queue age, actual CPU/GPU memory and collision continuity. The current **5 ms or greater fine-tile main-thread upload** is above the proposed 1–2 ms frame-work target; one commit per frame bounds frequency but does not split that upload. Low-end hardware has not been certified.
