# The command host

> **Kernel record, 6 October 2026, revised after the Lane P review the same night, and on 7 October for the kernel round (Lane A's gaps P1 to P8 in [kernel-host-gaps.md](../../companion/proposals/kernel-host-gaps.md), perception memory, goal jobs and `world.set_physics`).** `game/scripts/native/Kernel/CommandHost.cs` is the room's single command path for [game-command.schema.json](../../../contracts/game-command.schema.json). Manual controls, the companion adapter (A1/A2) and tests send `enfractal.command` and `enfractal.query` as JSON text; the host answers `enfractal.result`, and it always answers: anything unexpected becomes `internal_error`, never an exception out of `Handle`.

## Wiring

`RoomWorld` calls `Kernel.CommandHost.Attach(this);` once its room, player and companion exist. `Attach` creates the GDScript invention runtime (which creates and owns `creation_authority.gd`) with its workshop switched off (`workshop_enabled = false`: no INVENTIONS panel, editor or keys in the playable room, since the founder retired the workshop; the runtime still renders creations and runs their effects), points the runtime's `command_sink` at the host so any manual commit travels the same path, and adds a small approve/deny prompt. Saves go to `user://saves/rooms/<room_id>/<first 16 hex of the manifest hash>/inventions.json`, so a re-exported room starts a fresh file instead of refusing to load. **When other manifests of the same room have saves, the host tells the player** (`SaveNotice`, shown in the inventions card and printed as `COMMAND_HOST ...`): those creations were not loaded and stay on disk. Migrating them is a Run 2 item (below).

Callers: `string Handle(string message, string principal)` (canonical result text) or `JsonObject HandleObject(...)`. The principal is the caller's identity (`player:local` or `companion:local`), assigned by the trusted adapter; any other value is refused with `principal_unknown`, and any `principal`, `approval` or `approved_by` field in a message is `field_unknown`. The player's click calls `Approve(request_id)` or `Deny(request_id)`; nothing in a message can. `PlayerGoal(goal)` sends a goal command as the player for HUD keys, and `PlayerPhysics(preset)` sends `world.set_physics` as the player for the **G** key: the host sets `SmallPlayerController.WorldPhysicsRequest` when it attaches (and hands it back when freed), so the key has no path of its own. Without a host, G does nothing.

## Commands

| Op | Behaviour |
|---|---|
| `creation.place`, `creation.revise` | Through the authority. Placement `position_m` is a height hint: the host probes for the support just above it (a spot under the table stays under it); `on` must match the support. Rotation must be about the vertical axis. A revise with only a placement keeps the source; with only a source keeps the placement. `preview: true` runs the same checks and records nothing. |
| `entity.remove` | Creations only; captured objects wait for the sandbox verbs (`unsupported_capability`). |
| `protect.lock`, `protect.unlock` | Objects and creations, at most 256 locked at once. A locked thing cannot be revised or removed, even by the player, and is a no-build, no-effect zone. **`protect.unlock` from the companion is `permission_denied`, never held.** |
| `creation.activate` | Runs the creation's Use graph through the runtime; transient receipt. An activation that cannot fire (no Use trigger, a busy budget) keeps no receipt, so its retry runs instead of replaying a success. |
| `goal.set` | On `avatar:companion`: `follow`, `stay`, `come`, `look_at`, `point_at` (target or position). `go_to`, `fetch`, `wander` are `unsupported_capability` until A2, and so are `follow` and `come` with a target other than `avatar:player`, and `stay` with any target (the body follows and comes to the player only). A companion directing `avatar:player` is `actor_denied`. The result's `data` is `{actor, goal}`, plus, for the companion with a target, `target_seen` (`now`, or `remembered` with `last_seen_ago_s` and `may_be_stale`). **A goal with a target is a job**, and the result carries its `job_id` (below). |
| `goal.stop`, `effect.stop` | **Always apply**: never refused on revisions (expectations are ignored, malformed ones included), rate limits, capacity or a reused action id (a stop under a used id simply applies again). The player's `goal.stop` with no actor stops the companion and every running creation effect; naming an avatar stops that avatar's goals and effects. The companion's stops cover only its own goals and effects, and it may not name `avatar:player` (`actor_denied`). `effect.stop "all"` is every effect for the player and the companion's own effects for the companion. An effect belongs to whoever used the creation (timers and sensors: the creation's owner). |
| `room.checkpoint` | Compacts the durable ledger (below). Any principal; it changes no world state and does not move the revision; it never fails for a full ledger. Every committed answer carries `data.checkpoint_revision`: the first, every replay, and a replay after a later checkpoint compacted it. An optional `label` follows the text rule (80 characters). |
| `world.set_physics` | **Player-only** (`$defs/player_only_ops`): from the companion `permission_denied` at `$.op`, never held. `args.preset` is one of `world_physics_profile.gd` `PRESET_IDS` (`room_tuned`, `room_real`, `room_floaty`); anything else is `invalid_args` at `$.args.preset`, with the presets in `allowed`. Both bodies adopt the preset at once. Not saved in room state yet, so the receipt is transient and the room revision does not move. |
| `entity.grab/release/place/set_part/transform`, `effect.start`, `style.set`, `room.undo` | Validated structurally, then `unsupported_capability` naming the packet that will add them. `entity.release` will keep a durable receipt (putting a thing down is saved state); of these, only `entity.grab` and `effect.start` are transient. |

Order of checks: principal; **the companion's rate limit** (30 messages a second, before parsing, so invalid messages count too; stops are exempt, and with no token left only text that may be a stop is parsed at all); size and strict parsing (64 KiB canonical); envelope (expectations skipped for stops); the text rule over every string and key; fingerprint; **the companion's look** (every companion message but a stop takes its avatar's sight now and fills its perception memory; stops skip it, so the stops the rate limit exempts never cost a sweep of rays); **replay** (not for stops: a committed `(principal, action_id)` with the same fingerprint returns its receipt with `replayed: true` before any permission or revision check; durable receipts are found first, then compacted ones, then transient ones; different content is `action_id_conflict`); held approvals; argument structure; **player-only ops** (`protect.unlock`, `world.set_physics`: `permission_denied` for the companion); unsupported ops; `expected_revision` and `expected_entities` (skipped for stops; destructive ops must name one, and `expected_entities` must cover their targets and be in sight now); **perception** (a companion may name only what it can see now, the player's avatar included; only a goal that moves or turns it may aim at something it remembers); approval policy; execution.

The fingerprint covers the canonical command as received, so a retry that only adds `"preview": false` is a different command (`action_id_conflict`). The contract's README says so (Idempotency), and Lane A's mock does the same.

## Receipts

- **Durable** (place, revise, remove, lock, unlock, checkpoint): stored by the authority in the same atomic save as the state, keyed `principal|action_id`, with the contract fingerprint, op, time and approver. The host rebuilds every answer from that receipt, so the first answer and every replay are identical apart from `replayed`, and they survive a reload. **At most 2,048; the last 256 are the player's**, so a companion that fills its 1,792 can never block the player's lock, placement or moderation (`receipt_limit`, retryable, "a room.checkpoint compacts it"). `room.checkpoint` compacts every durable receipt to its revision and a 64-bit fingerprint prefix (at most 4,096 kept, oldest forgotten): it still replays and still refuses other content, and `receipt.lookup` answers `{found: true, compacted: true}`.
- **Transient** (goals, stops, activations and, while it is not saved, the world's physics; later effects and grabs, never a release): held by the host for the session, **at most 1,024 per principal, the oldest forgotten first**, so a transient command never fails for capacity and never answers a refusal after it has acted. The authority keeps the same per-principal bound for activations. `Transient()` refuses any op outside that list, so a durable op can never be answered with a transient receipt.
- **A stop never hides a receipt.** A stop applies under any action id and keeps a transient receipt under it; replay and `receipt.lookup` look at the durable receipt first, then the compacted one, then the transient one. A resent lock replays the lock, and `receipt.lookup` answers the lock, as the contract asks before a retry (gap P2).
- Failed commands consume nothing; a preview records nothing.

## Approvals

A companion `entity.remove` or `creation.revise` of a creation the player owns is held. The host answers `approval_required` (`retryable: true`) with `approval_needed.request_id` (128 random bits, 32 hex characters), a reason that names the entity id only (names are untrusted world text) and `expires_utc` five minutes ahead. Sending the same command again returns the same request; the same action id with other content is `action_id_conflict`.

A request **lapses as soon as** an entity it touches changes, or, for a command that named `expected_revision`, as soon as the room revision moves: `approval.status` answers `expired` with an `approval_mismatch` result at once, and the prompt drops it. Expiry gives `approval_expired`. On `Approve`, the held command commits under the companion's principal and action id with `approved_by: player:local` in the durable receipt; perception no longer applies, because the player approved it. If it can no longer be made as approved, the request ends `expired` with `approval_mismatch` (or `receipt_limit`), never `approved` with `ok: false`. **Denial, expiry and lapse are final for that action id**: resending it returns the same non-retryable refusal, which says to use a new action id. `approval.status` answers `pending`, `approved`, `denied` or `expired` (with the result once final) to the requesting principal or the player, and `target_not_found` otherwise. At most eight requests per principal wait at once.

## Queries and what the companion perceives

`room.describe`, `entities.list` (filters, `limit`, numeric `cursor`), `entity.inspect` (with `protected_by`), `observe` (radius up to 20 m, and **20 m when left out**: the founder's everything-in-line-of-sight rule; at most 100 entities and 50 texts, every name marked `untrusted: true`; the room shell is left out, since `room.describe` and `entities.list` cover it and it would use up the 100 places in a captured room; **a companion observes only through `avatar:companion`**), `receipt.lookup` (principal-bound; durable, then compacted, then transient), `approval.status`, `capabilities.list` (the contract's `{"items": [...]}` of `capability_summary`, empty until `effect.start` arrives in Run 3; a `cursor` other than `"0"` is `invalid_args`), `jobs.status` (below).

**Line of sight** ([PERCEPTION.md](../../companion/PERCEPTION.md)), with physics ray casts against the real colliders in place of the mock's boxes: from the avatar's eye camera, each entity is sampled at 15 points of its bounds (the centre, the eight corners and the six face centres, each pulled 1 cm or a quarter of the box inside); a sample is seen when the ray reaches it, or reaches the entity itself, first. Rays test only the world layer, so avatars and effects never occlude. The companion's own avatar and the room shell are always perceived. For the companion, `entities.list` lists only what it sees, `entity.inspect` of anything else is `target_not_found` byte for byte as for an unknown id, `room.describe` counts only what it sees, `observe` shows only what it sees, and every command naming an entity (`target`, `targets`, `placement.on`, `expected_entities`) is `target_not_found` unless it is in sight now. The player's queries see everything; the player's `observe` through `avatar:player` uses the same rule from the player's eye.

**Perception memory** (founder decision, 6 October: the companion remembers what it has seen and where, and says when that may be out of date; the contract's `entity_summary` fields since `7e2c779`; the mock's behaviour, ported with its suites):

- **Filled only by looking.** Every companion message but a stop is a look: its avatar's sight now is taken for the request and remembered, and arriving at a goal is a look too. Only the companion's own avatar fills it: never the player's queries, the player looking through the companion's eyes, or `Perceive` itself. The shell and the companion's own avatar are not remembered.
- **What is kept:** each entity's summary exactly as last seen, who protected it then, when (`Clock`) and at which room revision; at most `PerceptionMemoryEntries` (256) per companion, the least recently seen forgotten first (what is seen now is remembered afresh, nearest last). In memory only: never in a receipt, a snapshot or a save, and a new host (a new room, or a reload) starts empty. `SessionEvent(principal, "start" | "end")`, the hook the Run 2 bridge calls (the mock's `session_event`), and `ClearPerceptionMemory` clear it.
- **In results:** things in sight carry `seen: "now"`; things remembered out of sight carry `seen: "remembered"`, `last_seen_ago_s` (to 0.1 s), `last_seen_revision` and `may_be_stale`. `entities.list` lists both (filters apply to what was seen), `entity.inspect` answers from memory (with the remembered `protected_by`), `observe` adds `remembered` (out of sight, within the radius of where each was last seen, nearest first, at most 50), and `room.describe` counts only what is in sight. The player's results carry none of these fields.
- **One bit, never what changed.** On every look, a remembered thing out of sight that differs in any way from what was seen (moved more than 5 mm, edited, locked, renamed or gone) is marked changed until it is seen again; `may_be_stale` is that, or a memory `PerceptionMemoryStaleAfterS` (60 s) old. If the place it was last seen is in sight and it is not there, the memory is dropped: a thing removed out of sight is remembered as it was until its place is seen empty, and is then byte-identical to something that never existed.
- **Commands:** anything that changes or names an entity still needs it in sight now (`target`, `targets`, `placement.on`, `expected_entities`). Only `goal.set`'s `target` for a goal that moves or turns the companion (`go_to`, `look_at`, `point_at`, `come`, `fetch`) may be remembered. Such a goal aims at the memory alone, so its answer cannot say what became of the thing; the host re-checks on arrival.

**Goal jobs** (gap P7). A goal with a target runs as a job: the result carries `job_id` (`goal-000001`, numbered per principal, so an id says nothing about another principal's goals), and `jobs.status` answers `running`, `succeeded`, `failed` (with the failed `goal.set` result under its action id) or `cancelled`. A new goal for the avatar or a stop cancels it, and so does the body taking a newer goal (`CompanionAvatar.IntentSerial`). At most `MaxJobsPerPrincipal` (256) are kept per principal, the oldest finished dropped first; another principal's job id, like an unknown one, is `target_not_found`. On arrival the host re-checks from where the avatar is now, with its own sight: `succeeded` when the target is in sight within `ArrivalReachM` (0.15 m) of where the goal aimed (a followed or approached player counts wherever the player is); `failed` with `revision_conflict` (retryable) when it is in sight but has moved; `failed` with `target_not_found` when it is not in sight, moved out of sight and gone alike.

The host drives arrival itself for the goals the body has today, from `CompanionAvatar`'s public state: `look_at` and `point_at` arrive when the body faces the target within 3 degrees (`FacesLookTarget`), `come` when the body reaches the player (`ComeArrivedSerial`), and `follow` runs until replaced. **The seam for the A2 goal runner** (`game/scripts/native/Companion/`, Run 2): `RunningGoal(actor)` gives the running job's id, goal, target and aim; the runner moves the body for `go_to` and `fetch` and calls `ReportArrival(actor)` when it gets there; `GoalFinished(actor, job_id, state)` is raised for every finished job. The host keeps the job store, the arrival check and the query.

## Untrusted text

Every string and key in a request follows the project's invisible-character rule (`Kernel/KernelText.cs`, the same as `scripts/creation_text.gd`): controls, line and paragraph separators, every Unicode format character (Cf), U+034F, U+115F, U+1160, U+180B-U+180F, U+2028-U+202E, U+2060-U+206F, U+2800, U+3164, U+FFA0, U+FFF9-U+FFFB, the variation selectors U+FE00-U+FE0F and plane 14 are refused (`request_invalid` at the field's path), except the standard emoji markers where an emoji puts them (VS15 and VS16 directly after an emoji or a keycap base, at most one; ZWJ between two emoji, the first optionally with VS16 or a skin tone; the keycap after 0-9, # or *, optionally with VS16). Every text the host emits (names, categories, messages, field paths) has hidden characters replaced by spaces and is cut on a code point, never inside a surrogate pair. Anchored patterns use `\A` and `\z`: .NET's `$` matches before a final newline.

## Error mapping

The GDScript kernel's codes map onto the contract's as in [contracts/README.md](../../../contracts/README.md), with these additions: `target_locked` and `protected_zone` → `target_protected`; `room_bounds`, `surface_unavailable`, `surface_uneven` → `out_of_bounds`; `surface_mismatch`, `already_locked`, `not_locked`, `target_invalid`, `label_invalid` → `invalid_args`; `unlock_denied` and `activation_context` → `permission_denied`; `save_size` → `state_limit`; creation compiler codes → `invalid_args` with `field_path` under `$.args.source`.

## Saves of a re-exported room: proposed migration (Run 2)

Today a new manifest hash means a new save folder, and the old one is only reported. The proposal: on loading a room with no save under its own hash, offer to bring creations over from the newest save of the same `room_id`. Each saved creation is recompiled and its placement re-validated against the new room (bounds, the surface query, the ceiling); those that pass keep their ids and revisions, the rest are listed for the player and left in the old file. Locks on objects that still exist carry over; locks on missing objects drop. The receipt ledger starts compacted (a checkpoint at the migrated revision), so old action ids still refuse conflicting reuse. The old file is never modified, and the migration is one player-confirmed step, never automatic.
