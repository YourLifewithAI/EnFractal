# Phase 3 manual invention: primary-source implementation notes

> **Kernel record.** This describes the creation kernel as built for the retired Barton workshop. The kernel is kept; its plot bounds, terrain sampler and legacy fixture body are generalized for rooms in R0 (see the [room-scale direction](../../ROOM-SCALE-DIRECTION.md)). Scene, launcher and checkpoint references below may point at files now on the `geography-era-final` branch.

Checked **2026-10-02** against Godot **4.7** documentation and Roblox Creator Hub. This note informs the [manual invention contract](manual-invention-contract.md); it is not an acceptance score or proof that the current playable build passes its tests.

| Layer | Primary-source finding | Decision and specific acceptance check |
|---|---|---|
| Private preview | A Godot viewport normally shares its parent's `World3D`; assigning its own world separates both rendering and physics. A `SubViewport` can stop rendering with `UPDATE_DISABLED`, and a viewport capture needs at least one completed draw. [Godot: Using Viewports](https://docs.godotengine.org/en/4.7/tutorials/rendering/viewports.html), [SubViewport](https://docs.godotengine.org/en/4.7/classes/class_subviewport.html) | Keep the editor draft in a `SubViewport` with its own `World3D`; never add preview parts or effect fields to the live map. On close or replacement, stop its update and simulation, free the previous assembly, and verify no preview collision/effect survives. Measure preview frame and memory cost on the low profile. `UPDATE_ALWAYS` while hidden should not be assumed free. |
| Editor input | Godot's `Control` handles focused GUI events, but movement that polls `Input` each physics tick is a separate path. Controls can consume handled events, and keyboard/gamepad focus needs an intentional route. [Godot: Control](https://docs.godotengine.org/en/4.7/classes/class_control.html), [Input examples](https://docs.godotengine.org/en/4.7/tutorials/inputs/input_examples.html) | Gate the player controller's movement/jump polling while the modal editor is open, suppress old workshop shortcuts, and restore focus/mouse capture on close. Test held WASD/Space during editor opening, typing in fields, Escape, Tab navigation, and returning to play. |
| Character motion | `CharacterBody3D` is script-driven and `move_and_slide()` uses its velocity in the physics step; it modifies velocity after collisions. [Godot: CharacterBody3D](https://docs.godotengine.org/en/4.7/classes/class_characterbody3d.html) | Integrate capped wind and glide into one `_physics_process()` movement path. Keep creation-induced velocity distinct so revocation can clear it without erasing ordinary movement; test collisions, slopes, map-edge recovery, 30/60/120 Hz results, and consent changes mid-flight. Do not present this as general aerodynamics or free rigid-body physics. |
| Proximity and effects | `Area3D` overlap lists update during the physics step, not immediately after a body moves. [Godot: Area3D](https://docs.godotengine.org/en/4.7/classes/class_area3d.html) | For v1's two known actors, a bounded distance check per physics tick is simpler than relying on same-frame overlap results. Recheck target consent, plot/field reach, active instance, and effect budget when each tick applies a field; a past successful trigger is insufficient authorization. If `Area3D` is added later, test the one-step latency explicitly. |
| Capability composition | Roblox's capability documentation illustrates an explicit list of permitted operations; its security guidance also warns against dynamically loading code or arbitrary instance paths from client arguments. This is an architectural comparison, **not** a Godot feature. [Roblox: Script capabilities](https://create.roblox.com/docs/scripting/capabilities), [Client-server boundary](https://create.roblox.com/docs/scripting/security/client-server-boundary) | Keep creations as bounded data: approved parts, typed operation nodes, finite parameters, acyclic wiring, and a compiler-derived cost/bounds/hash. Templates use the same compiler as manual editing. Reject scripts, arbitrary resources, unknown keys, forged grants, cycles, and excessive graph size; never execute source text or treat local IDs as permission tokens. |
| Publication and permissions | Godot says multiplayer APIs do not secure gameplay logic automatically: clients remain untrusted; the server validates arguments and frequent actions. Roblox independently recommends context/permission, type/structure, value, and rate-limit checks on server-received actions. [Godot: Secure multiplayer design](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html#secure-multiplayer-design), [Roblox: Client-server boundary](https://create.roblox.com/docs/scripting/security/client-server-boundary) | One trusted host command service must recompile source at place/revise time, derive owner/height/cost itself, check complete rotated bounds and effect reach, verify ACL/consent and quotas, and return stable receipts. A client-sent principal, hash, preview result, cost, or target must never confer authority. Rate-limit even valid triggers. |

## Current local fixture versus a hosted world

The new `creation_compiler.gd`, `creation_authority.gd`, `invention_editor.gd`, and `invention_runtime.gd` follow the intended separation in progress: data source → compile → host command → live interpreter, with a distinct editor preview. The `guest_player` mannequin is a deterministic local consent test. It is **not** a connected second player, authenticated identity, or proof of remote synchronization. The currently proposed `local_player` principal is supplied by the local adapter. A hosted adapter must bind an authenticated peer to a principal on the server, pass only source and intent into the same service, and validate every command and live effect there. Godot documents authentication separately from gameplay security in its [multiplayer guide](https://docs.godotengine.org/en/4.7/tutorials/networking/high_level_multiplayer.html#authentication).

The v1 feature limit is appropriate for a first manual loop: grounded or avatar-mounted assemblies; fixed primitive parts; `interact`, timer and proximity triggers; bounded wind, rotor spin, light, and glide. General script execution, free dynamic rigid bodies, joints, cross-world wires, open-ended AI proposals, shared undo, and remote publishing remain later capabilities that each need their own contracts and tests. The independent Phase 3 rating should wait for a stable editor and playable tests; this source review does not assign one.
