# Cross-system contract v0.1 (proposed)

**Status:** E02 interface proposal, 1 October 2026. This document names the shared meanings and small test envelopes for map, rendering, physics, creation, persistence, networking and AI/MCP agents. It is **not a shipped network protocol or approval to open a hosted world**. Field names below are proposed `snake_case` JSON names; exact cross-language canonical encoding, schema fixtures, migration rules and reviewer sign-off are remaining E02 work. The [decision record](decisions.md) lists product assumptions. The [world vision](../../WORLD-VISION.md) and [structured-world plan](../../roadmap/research/11-structured-world-and-style-system.md) supply the intended behavior.

## Version and ownership rules

- `contract_version` uses major.minor.patch. A major change can alter meaning or required fields; a minor change adds an explicitly optional, inert field; a patch clarifies wording without changing accepted behavior. Unknown major versions fail closed. A generator/style version is separate from this schema version.
- The **map builder** owns immutable geographic packages and evidence records; the **one creation compiler** owns accepted capability/semantic/style output; the **world authority** owns permissions, placement, movement consequences, revisions and durable action receipts. A client, manual editor, AI model and MCP adapter may draft the same typed request, but cannot mint authority.
- Persist canonical intent, semantic parts, relationships, source references, generator/style pins, and accepted actions. Render meshes, LODs, collision shapes and previews are rebuildable derivatives. Never silently regenerate an older saved world with changed rules or source data.
- The currently implemented `enfractal-map-v0` package and `enfractal-world-state` save schema version 2 are **prototype formats**, not wire compatibility promises. The current local save validates a base-map pin and idempotent edits but is neither server authority nor crash-tested hosted durability.

## Coordinates, identity and revision

| Name | Proposed meaning and validation |
|---|---|
| `world_id` | Opaque, stable identity of one independently writable world. Home Earth has one canonical ID; a private sandbox has another even when it shares base map bytes. Never derive authority from its spelling. |
| `frame_id` | Immutable ID of a geographic-to-local transform with a documented origin, horizontal CRS, axes, vertical datum/geoid and transform implementation/version. A changed interpretation needs a new frame ID and explicit migration. Never silently reinterpret saved local coordinates. |
| Global location | Future persistent position uses finite double-precision Earth coordinates plus a declared geodetic and vertical reference, converted by a versioned frame. The Barton prototype cannot yet claim this: its manifest uses EPSG:32614 UTM grid offsets for horizontal position, **not an Earth-centered or topocentric east-north-up (ENU) frame**, and the exact source vertical datum is unresolved. |
| Local location | In the current Barton package: metres, `+X` is increasing **UTM grid easting**, `+Z` is decreasing **UTM grid northing**, and `+Y` is decoded DEM height relative to the package origin. These are approximately east/south/up near the pin, not geodetic true east/north/up. Godot positive yaw about `+Y` turns local `+X` toward `-Z` (grid north); it is not automatically a true-north bearing. Distances, speed, acceleration, mass, force and time must declare SI units (`_m`, `_mps`, `_mps2`, `_kg`, `_n`, `_s`) rather than unlabelled numbers. All numeric request values are finite and bounded by the named capability. |
| `base_ref` | Immutable `map_id`, `heights_sha256`, `features_sha256` and digest of spatial metadata. Hashes identify data and placement frame, not ownership. The local state v2 already pins these; the exact cross-language spatial-metadata canonicalization needs a golden fixture before interchange. |
| `world_revision` | Monotonic revision of accepted consequential edits in one world. Commands carry an expected revision; stale commands fail or return a conflict with current safe metadata. |
| `world_rules_revision` / `world_rules_hash` | Monotonic rule revision and immutable content hash of **one world's** approved `WorldRules` profile. The profile declares gravity and ambient wind in SI units, supported capabilities, and relevant safety/budget bounds. Compare a revision only with its `world_id`, `frame_id` and authority epoch; a destination world can have a smaller number without being stale. Only trusted world authority may set it. Stage a rule change for a tick boundary and revalidate pending commands/previews. A portal transfer explicitly binds the destination rule hash at activation. Current E07 local gravity/wind presets and setter are a test seam, not permanent numeric values or a portal API. |
| `entity_revision` / `permission_revision` | Per-object and per-parcel/ACL revisions for narrower compare-and-set checks. The authority reads current permissions at commit; a claimed owner or old grant in a request is never sufficient. These revisions are not in the local platform save yet. |
| `collision_revision` / `visual_revision` | Monotonic revisions of derived collision and visual content for an affected tile/region. Visual LOD may differ by client without changing semantic state or collision. For an accepted edit, stage both derivatives against the same `world_revision`; keep the prior collider active until the replacement is ready; activate an agreed pair at a named authoritative tick. A provisional E06 worker-thread mesh build is only a local spike, not this production handoff. |
| `tile_id`, `cell_id`, `parcel_id` | Separate geographic storage, simulation ownership and permission addresses. Never treat equal-looking coordinates as equal authority. |

The present `barton_creek_v0` package centers on latitude **30.250924**, longitude **-97.810494**, spans 4,096 m and samples terrain at 2 m. `mapbuilder.geo.MapConfig.to_local()` projects longitude/latitude with EPSG:32614 and subtracts the **full-precision computed** projected center `(614439.4592043258, 3347188.813376341)` m: `x = projected_easting - center_easting`, `z = center_northing - projected_northing`. The manifest records that center rounded to millimetres as `[614439.459, 3347188.813]`; that rounded pin value is **not** what the builder uses for conversion. A reader must use one named convention consistently, never mix a rounded-origin conversion with full-precision feature coordinates. The current Python coordinate round-trip fixture uses a **0.001 m** absolute tolerance; this is a test tolerance, not the DEM's measurement accuracy or permission to shift saved objects. The package records `height_origin_m: 203.7862`; local `Y` is decoded DEM height minus that origin. The source mosaic's exact vertical datum is not established, so local `Y` is suitable for this fixture but not yet for global geodetic interchange.

For this local terrain, `surface_height_at(x,z)` has a precise collision meaning. Valid queries are finite points in the closed square `[-2048,2048] × [-2048,2048]` m; outside or non-finite input returns `NaN` in the local Godot API, never a clamped safe floor. A future JSON/wire API must return a typed error rather than serialize `NaN`. Grid columns grow east and rows grow south. In each 2 m cell let `a` be northwest, `b` northeast, `c` southwest and `d` southeast. The collider uses triangles `a-c-b` and `b-c-d`, split on the northeast-to-southwest `b-c` diagonal; normalized local fractions with `fx + fz <= 1` select the first triangle, otherwise the second. Their common edge agrees. A query exactly at `+2048` belongs to the final cell with fraction `1`, while any larger coordinate is outside. `height_at(x,z)` is bilinear visual sampling and may differ on steep cells; movement/spawn and physical placement use `surface_height_at`. `height_at_grid()` clamps integer indices for internal edge sampling but does **not** define outside-world collision. `normal_at()` is a smoothed bilinear finite-difference normal, **not** the authoritative triangle normal for contacts. Visual mesh LOD never changes the fixed collision surface.

A changed horizontal transform, origin, axis convention, vertical datum/geoid conversion or height decoder requires a new `frame_id` and corresponding base pin, with an explicit migration for existing placements. A changed collision-surface algorithm or cell diagonal requires at least a new versioned surface-algorithm field in the base pin and a new collision revision; it cannot silently reuse the old save interpretation even if `heights.r16` bytes are identical. The next schema must include a hashed machine-readable vertical reference, including an explicit `unknown`/`local_only` state for Barton; a prose limitation is not enough. The current manifest/spatial digest does **not** yet include the transform implementation, geoid or triangulation algorithm, so this is a requirement for the next schema, not a claim that existing saves enforce it. A visual-only LOD change may update `visual_revision` without changing the authoritative frame or collision surface.

### Narrow phase 1 local fixture contract

Agents may rely on the immutable `barton_creek_v0` package's existing manifest, payload hashes, UTM-offset formula, 2 m grid, the piecewise-planar collision query above and the local state schema v2 for **tests on this package only**. Treat its `collision_revision: 0` as immutable terrain and use the existing workshop's `edit:<action_id>` IDs solely for local save/reload. A local test can assert that source grid corners, positive outer edges and adjacent collider patches agree; a second region can use the same explicit grid rules but must carry its own map/frame pin and documented datum limitation. The synthetic [second-region map fixture](../phase1/map-contract.md) exercises index and height decoding, not a globally interchangeable frame. Global ECEF/ENU encoding, vertical conversion, cross-language canonical JSON/hash vectors, hosted authority and cross-region migration remain open E02/E05 gates. This bounded fixture contract does **not** freeze the proposed network envelope below.

## Semantic objects and geographic evidence

An authority-issued `object_id` is stable across edits and graphics profiles; `part_id` and `relationship_id` are stable within the object/world and survive unrelated regeneration. Their string prefixes may help debugging but have **no permission semantics**. Source-feature IDs are namespaced by map package, source layer and native feature ID, with a segment discriminator when extraction splits one source feature. The current source records (for example, OSM IDs) are not yet a full stable semantic object catalogue. Current local player objects use `edit:<action_id>`; migrating that convention requires a fixture before shared use.

Each significant semantic part minimally records `kind`, `object_id`, `part_id`, `world_id`, `frame_id`, local transform and bounds, owning parcel, editable parameters, material role, collision/interaction role, `generator_id`, `generator_version`, `style_family`, `style_version`, deterministic seed, and affected-bounds/relationship references. Supported relationships are typed (for example `contains`, `attaches_to`, `supports`, `crosses`, `path_connects_to`) and have stable IDs. A join generator may change only declared affected parts/bounds; it must preserve manual exceptions and fail when the necessary neighboring part is unavailable or unauthorized. The approved low-detail representation and cost estimate belong with the generated artifact.

Evidence is separate from aesthetics. Use a `provenance` record with `classification` from `source_backed`, `estimated`, `authored_interpretation`, or `player_change`; `confidence` from `high`, `medium`, `low`, or `not_applicable`; and source IDs, observation/acquisition date, rights/license reference, resolution/uncertainty, and correction history where applicable. `player_change` records the authenticated creator ID and action ID; it is not a claim that the changed geometry reflects the real place. A procedurally placed tree or guessed roof height cannot be labelled `source_backed` merely because nearby roads came from a source map. An art asset may have its own license and author; these claims are independently checked before distribution.

## Portable design versus placed instance

The portable `blueprint` uses its own local origin and SI dimensions. It declares a schema version, required capabilities, semantic parts/relationships, approved asset/material roles and generator dependencies. It contains no live `world_id`, parcel ownership, active avatar, permission grant, currency or authoritative placement. A source design hash and compiler/rules/style hashes identify precisely what was validated. Importing it into another world produces a **new destination-local instance** after recompilation under that world's rules; Home ownership and permissions do not travel.

The placement request names `world_id`, `frame_id`, destination `parcel_id`, a compiled artifact hash, a finite local transform, expected world/object/permission/rule revisions and a unique `action_id`. The authority supplies principal identity from the authenticated session, checks current parcel ACL/capacity/physics/style budgets, and alone issues object IDs and a durable receipt. The same command gateway serves manual UI and approved AI/MCP calls. A preview reserves no live authority and cannot mutate Home. An AI suggestion is draft data, never publication consent.

Proposed future placement envelope (illustrative; the current local `CreationOps.prepare()` does **not** accept this JSON):

```json
{
  "contract_version": "0.1.0",
  "action_id": "a_7bb53e2b_5f78_4466_a52b_9987cd0789d9",
  "target": {"world_id": "home_earth", "frame_id": "barton_local_1", "parcel_id": "workshop_12"},
  "expected": {"world_revision": 18, "permission_revision": 3, "world_rules_revision": 2,
               "base_ref": {"map_id": "barton_creek_v0", "heights_sha256": "<64 lowercase hex>",
                            "features_sha256": "<64 lowercase hex>", "spatial_manifest_sha256": "<64 lowercase hex>"}},
  "operation": {"type": "place_blueprint", "artifact_sha256": "<64 lowercase hex>",
                "position_m": {"x": 12.5, "y": 0.0, "z": 341.0}, "yaw_deg": 90.0}
}
```

Here angle `90` rotates local `+X` toward **UTM grid north** (`-Z`), not necessarily true geographic north. The example hash placeholders are explanatory, not valid wire values. The authority may reject the proposed `y` if it does not match the collision-anchored placement rule; it never trusts client height, actor ID or cost claims. A later `revise_part` command names stable object/part IDs and expected `entity_revision`, preserving unaffected parts. The current local test contract is narrower: `place_platform`/`revise_platform`/`remove_platform` over a single authorized test plot, then a translated `place`/`update`/`remove` command in `WorldState`.

## Action, transport and error semantics

An `action_id` is generated before a consequential attempt and scoped to authenticated principal and target world. Its fingerprint includes the canonical command, target and expected revisions. After authenticating the caller and enforcing basic request-size/syntax limits, the gateway looks up a **previously committed** `(principal, world_id, action_id)` and compares its original fingerprint **before** rechecking current rules, ACL, terrain, target existence or publication-grant expiry. An identical replay returns the original receipt, even after those conditions change or the target is later removed; a changed command returns `action_id_conflict`. Receipt lookup still requires that the caller is the original authenticated principal or an authorized operator; possession of an action ID alone reveals nothing. A timeout means **unknown outcome**, never proof of failure. Only a committed and recoverable action receives an `accepted` receipt. The proposed receipt carries `action_id`, `object_id`, committed `world_revision`, `world_rules_revision`, pinned artifact/rule/base hashes, an authority epoch, and `replayed`; a failed response carries stable `code`, `retryable`, optional `field_path`/safe bounds, current relevant revision and a correlation ID. No stack traces, private state, raw prompts or credentials appear in ordinary errors. The local `CreationOps.prepare()` currently recompiles before `WorldState` checks its action ledger; that ordering is **not** a conformant hosted replay gateway.

The gameplay transport must be maintained, authenticated and encrypted with server identity validation. Input messages name session and sequence, world/frame and authority epoch; the server validates freshness, rate, region capacity and current permissions. A client sends intentions, not claimed final positions/forces, successful payments or ownership. Reconnect replaces the prior active session of a logical avatar. Presence and portal transfers have one fenced authority at a time. Server tick cadence and snapshot rate are engineering hypotheses, not contract constants until E03/E09 measurement. MCP runs over a separate restricted command path and never transports real-time movement.

| Code | When returned | Safe next step |
|---|---|---|
| `unsupported_contract_version` | Unknown major/required field semantics | Upgrade or migrate explicitly. |
| `invalid_number` / `parameter_out_of_range` | NaN, infinity, missing unit or parameter outside a capability bound | Correct named field and resubmit with a new action ID if command content changed. |
| `outside_frame` | Finite physical query/placement outside the closed local collision extent | Keep movement at a loading boundary or recover to a validated point; never clamp an outside query into apparently safe terrain. |
| `base_or_frame_mismatch` | Package/frame differs from the pinned world | Load the correct base or run reviewed migration; never reinterpret placement silently. |
| `revision_conflict` / `permission_changed` | Expected state or ACL is stale | Reinspect, preview and reapprove where needed. |
| `world_rules_changed` | World physics/capability profile changed after draft or approval | Recompile and preview against current rules before publication. |
| `permission_denied` / `unknown_handle` | Current authenticated principal lacks access | Do not reveal a private object's existence through error detail. |
| `unsupported_capability` / `unsupported_generator` / `style_budget_exceeded` | Compiler cannot validate the requested behavior or representation | Choose an approved component/material or reduce bounded cost. |
| `region_capacity` / `collider_not_ready` | Admission or authoritative terrain is unavailable | Queue/retry as directed; do not walk through missing collision. |
| `action_id_conflict` | Same ID, different command fingerprint | Generate a new ID after reviewing state. |
| `commit_unknown` | Client lost reply or authority is reconciling | Query status by action ID; never invent a second placement. |

Unknown operation names, references, required fields, executable extensions, duplicate IDs, cycles, non-finite numbers and unbounded arrays fail closed. Exact maximum sizes, code spelling, canonical JSON profile and golden error fixtures must be agreed by the compiler, map, persistence, network and MCP reviewers before calling v0.1 frozen. The local workshop has different current error spellings and does not imply this table is implemented.

Concrete proposed conformance cases for the example placement command:

| Request change or retry | Required result |
|---|---|
| Send the identical `action_id` and identical command after losing the first reply, after a rule/ACL/terrain change, after target removal, or after the original publication grant expires | Return the original object ID and committed revision with `replayed: true` to the original authenticated principal; create nothing new and do not demand a fresh grant. |
| Reuse that `action_id` but change `position_m.x` to `13.5` | `action_id_conflict`; do not modify the original object. |
| Submit `expected.world_rules_revision: 1` while the authority has revision `2` | `world_rules_changed`; discard the old preview and require current-rule validation. |
| Submit `position_m.x: "NaN"` or an out-of-range finite coordinate | `invalid_number` or `parameter_out_of_range`, with `field_path: "/operation/position_m/x"`; no mutation. |
| Submit a guessed private part handle through manual UI or MCP | The same `unknown_handle` response without private object details; no mutation. |

For the **implemented local-only** fixture, a minimal accepted intent instead has the shape `{"op":"place_platform","action_id":"demo_1","expected_revision":0,"x_m":0,"z_m":350,"yaw_deg":0,"width_m":2,"depth_m":2}` when its test plot and terrain allow it. `CreationOps.prepare()` adds the trusted local actor/plot and produces a `WorldState` command; `WorldState.apply_validated_edit()` returns a revision and `edit:demo_1` ID. That behavior is useful test evidence, not a hosted durability or authorization guarantee.

## AI/MCP boundary and minimum data policy

The developer coding agent, optional player creation assistant and any later visible avatar agent are three distinct identities/environments. The player interface may inspect authorized parts, draft typed edits, validate, preview and request publication through the same gateway. Publication needs a UI-issued review grant bound to principal, world, parcel, artifact hash, revisions and expiry; a model cannot create that grant. A guessed ID, expired grant or changed draft fails. No player tool accepts shell commands, arbitrary code/shaders, SQL, filesystem paths, provider credentials or unreviewed fetch URLs. QGIS MCP, if used, remains an offline developer map-preparation tool and is never exposed to players. MCP protocol/SDK revisions and two-client compatibility still require implementation tests.

Minimum data inventory for a private alpha: account/auth identifiers and revocable session grants; display identity; worlds, parcels, semantic edits and receipts; invitations/blocks; moderation reports and their bounded evidence; operational metrics and action/correlation IDs; optional consented research feedback; optional AI usage/cost counters and draft artifacts. Collect contact information only if the invite/support flow actually needs it. Routine logs include reason codes and identifiers, **not credentials, raw prompts, private chat transcripts, unrelated files or full location histories**. Keep AI prompts transient by default; saving or sending them to a provider needs a clear user action and disclosure. Authorized world edits and reports have different retention needs, so deletion/export and moderation holds need explicit treatment. Before tester enrollment, the founder must choose and publish concrete retention/deletion periods, provider disclosures, access controls and incident process; no period or legal compliance claim is approved by this proposal.

## Review gates without dependency cycles

**Narrow phase 1 local fixture handoff:** the map and physics reviewers can check the existing Barton manifest, full-precision conversion convention, inclusive boundaries, fixed `b-c` collision diagonal, outside-query error semantics, hash-pinned local save, and a second synthetic region's round trips. The art/runtime reviewers can use those facts for local terrain and rendering work. This handoff does not imply an ENU global frame, certified source vertical datum, hosted edits or approved cross-language hash. The tests and documents exist or can be written against the present fixture; no future compiler, database or MCP server is prerequisite.

**Full E02 contract closure remains open:** map, art, physics, persistence, network and MCP owners must agree on explicit versioned field definitions, a machine-readable vertical reference and surface-algorithm pin, cross-language canonical bytes/hash vectors, numeric tolerances, stable error catalogue, replay order, and one migration example. Review paper command vectors for placement, rule change, stale ACL and uncertain commit; do **not** require production services merely to approve their interface. Until these are resolved, v0.1 is a coordination proposal, not a frozen production schema or a passed phase 0 gate.

**Later implementation conformance belongs to dependent packets:** E08A/E11 test semantic joins and the single compiler; E09/E13 test identity, authority and transport; E15 tests durable replay and recovery; E18/E19 test transfer fencing; E21–E25 test manual/AI/MCP equivalence and grants; E06/E08 test visual/collision revision activation and low-detail readability. Those systems must demonstrate the examples above after they exist, but their implementation tests cannot be an E02 prerequisite.
