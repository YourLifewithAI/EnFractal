# Companion security boundary

What the companion can and cannot do, where each rule is enforced, and the test that proves it.
Threat model: the model driving the companion may be persuaded by anything it reads (a sign in the
room, an object's name, a crafted creation) or may simply be wrong. Anything that can read the
session file can also skip the MCP adapter and talk to the game directly. So every rule is enforced
by the game host; the adapter repeats the rules it can check alone, to fail fast; and the server
process is locked down so that even a hijacked server cannot reach files, processes or the network.

## Layers

| Layer | Enforces |
|---|---|
| MCP surface (`server.py`) | Only contract ops are tools; player-only ops have none. No resources, prompts, completions, logging or sampling. Fixed instructions and descriptions that never include world text. |
| Adapter (`server.py`) | Builds every contract message itself. Refuses unknown fields, identity and approval keys at any depth, actors other than the companion's own avatar, oversized messages and creation sources, and floods (stop ops exempt). Validates every outgoing message against the contract and every incoming result (contract-valid, this principal, this room, this op and id) before relaying it. Returns results as one ASCII-escaped JSON line after a fixed preamble. |
| Link (`link.py`) | Loopback only, a per-launch 256-bit token proven by mutual HMAC (never sent), the principal bound to the connection, one companion at a time, handshake timeout and lockout, strict frames with size limits, no frame type for approvals. |
| Host (`mock_host.py`, then P1's `CommandHost`) | Everything, again: the contract schema and size limits, authority keys anywhere in args, room id, player-only ops, actors, entity existence (one answer for unknown, removed and foreign ids), revisions, idempotency, approvals, locks, budgets, rate limits, sanitised world text, contract-valid results. |
| Process (`lockdown.py`) | Environment scrubbed to `SYSTEMROOT`/`WINDIR`; a PEP 578 audit hook refuses file writes, reads outside the Python installation, the package, the contracts and the session file, process creation, non-loopback connections and lookups, URL fetching, the registry, sqlite and environment changes. |

The process lockdown is defence in depth inside Python, not an operating-system sandbox: native code
could get around an audit hook. The MCP client should launch the server as the player's ordinary
account with no extra privileges, and the founder's main Claude Code profile is a developer
assistant with far wider powers than the companion; for play, a separate game-only client profile
that has only this server is the recommendation from the earlier [AI and security study](../research/05-ai-mcp-and-security.md).

## Boundary-test report

Run: `uv run --project companion --locked python -m unittest discover -s companion/tests -v`.
Every result the mock host emits during the suites, and every tool result the MCP tests receive, is
also checked with `contracts/validate.py`.

## Policy numbers (founder decisions; current values are recommendations)

| Setting | Recommended default | Where |
|---|---|---|
| Companion commands held for the player's click | `entity.remove`, `entity.transform`, `creation.revise`, `room.undo`, `style.set` | `HostPolicy.companion_approval_ops` |
| Approval lifetime | 5 minutes; lapses when a touched entity changes | `approval_ttl_s` |
| Pending approvals per companion | 3 | `max_pending_approvals` |
| Command rate | 2 per second sustained, bursts of 10 (stop ops exempt) | host `HostPolicy`, adapter `Adapter` |
| Query rate | 10 per second sustained, bursts of 30 | same |
| What `observe` sees | Objects, creations, avatars and effects whose bounds are within the radius (default 3 m, contract maximum 20 m) of the companion; no line-of-sight test yet; shell parts omitted | `observe_default_radius_m` |
| What the room-wide queries see | `entities.list` and `entity.inspect` cover every entity in the room, not only what the companion can perceive | mock host |
| Effects | At most 4 running per principal; wind up to 5 m/s, glow intensity up to 1 | `max_effects_per_principal`, `CAPABILITIES` |
| Carry limits | Companion 2 kg, player 0.5 kg | `carry_limit_kg` |
