# Single-player platform, engine and companion integration

> **Decision recorded later on 2 October 2026:** The founder selected native Godot .NET and C# for S0–S6. The comparisons and 36-hour experiment plan below are retained research, not active work. Reopen alternatives only for demonstrated need. See the [accepted ADR](../../engine/decisions/0001-native-godot-csharp.md).


Planning and primary-source verification date: **2026-10-02**. Repository baseline inspected: `750ef88`. This is a decision proposal, not an implementation report or benchmark. The work caps below limit investigation effort; they are not delivery estimates.

## Decision to make

Choose the platform that best supports a compelling **single-player world with an embodied, customizable AI companion**. The companion is central to the creative experience: the player can ask for a hurricane, a flood, a rideable dragon, a rampage through an expendable castle, or a hillside of mushrooms. Those requests become understandable, bounded world actions governed by the same baseline rules and protection settings as direct player actions. Multiplayer belongs at the end of the roadmap, after this experience works and is worth sharing.

Browser delivery and native delivery remain candidates. Browser reach must not be dismissed before testing, and native delivery must not win merely because older planning assumed it. Likewise, browser convenience does not establish that the complete creative experience fits every browser or device. Evaluate the player's actual interaction, appearance, recovery and accessible hardware together.

The implemented baseline is **Godot with GDScript, Python tooling and Godot shaders**. `game/project.godot` currently selects GL Compatibility. C# is an undecided proposal from earlier research, not an adopted runtime. Preserve the working baseline while gathering evidence. This note reopens the earlier native-first/C# recommendation. Read [02-performance-and-stack.md](02-performance-and-stack.md) alongside this decision: unmeasured budgets remain hypotheses, and multiplayer infrastructure is deferred.

## Current geographic and avatar specimen

The first-location choice is now the Pfluger Pedestrian Bridge / Lady Bird Lake district, bounded by 6th Street, Barton Springs Road, Congress Avenue and MoPac; Barton Creek content development is on hold. Test a **0.30 m player avatar in meter-scale geography**, including low camera height, curbs/roots, bridge decks, foliage occlusion and appropriately retuned locomotion. Both candidate engines must use this same scale and detail workload. Use a labeled synthetic or preserved Barton specimen if public-source auditing is not ready; do not claim it is a reconstruction of Pfluger. This does not increase the experiment cap. [Location/scale study](15-pfluger-district-and-small-avatar.md).

## What creative freedom requires

Represent a creation as a composition of world primitives: geometry, materials, bodies, joints, movement abilities, effect volumes, terrain changes and bounded behaviors. A dragon can have a form, locomotion, a mount point and an allowed attack; a storm can combine a wind field, rain, sound and water effects. The exact supported vocabulary must expand through playable examples. Neither a browser nor a native engine automatically provides unrestricted simulation or arbitrary creature generation.

Keep one simulation owner in the single-player process. Manual controls and companion requests enter the same command validator. It checks the selected world rules, protected objects/areas, permitted effects, resource costs, current world revision and cancellation state before applying changes. The model proposes actions; ordinary game code runs movement, collision, effects and recovery. Model latency must not sit inside the physics loop.

Start with bounded storm and water representations whose interaction is clear. Full atmospheric or fluid simulation across an enormous real-world region is a separate research problem. Render quality may scale by device; the meaning of an accepted action and its protection checks must remain consistent. If a device cannot handle an action's declared simulation budget, offer a smaller explicit scope before applying it. Do not silently turn off meaningful physics or protection to preserve frame rate.

Single-player makes local saves, pause, undo and creative experimentation more tractable. It does not make imported worlds, images, descriptions or model output trustworthy. Keep the companion's authority confined to game-scoped resources and operations; unrelated connectors are outside the supported profile. Give the player an immediate stop control, a visible action preview when needed, and a recoverable checkpoint before substantial destructive changes.

## Browser, native and streamed play

The following tradeoffs are engineering assessments based on the documented platform capabilities below. They are not measured performance rankings.

| Dimension | Game running locally in a browser | Native game running locally |
|---|---|---|
| Reach and first use | A shareable link removes a conventional installer and enables rapid trials. Browser/device compatibility, download time, touch controls and accessibility still require testing. | An installation/update step and per-platform packaging add friction. The application can expose deeper local integrations. |
| Graphics and simulation | Uses the player's CPU/GPU through browser APIs; browser access does not provide cloud computing. The chosen engine/backend restricts available rendering features. | Can use the engine's native backends and platform facilities. This creates options, not a guarantee that demanding effects fit low-end hardware. |
| Memory | Budget game allocations, assets, browser overhead and GPU resources together. A WebAssembly heap measurement is not total application memory. Browser lifecycle and GPU loss need recovery paths. | More direct profiling and lifecycle control; still shares finite RAM/VRAM with the OS and other applications. Bounded residency is necessary here too. |
| Saves and offline play | Local storage can support real saves, with export/import and optional synchronization. Browser storage needs failure handling and recovery. Cached offline assets do not make a remote AI provider available offline. | Ordinary local save files and backups fit naturally. A remote provider still requires connectivity unless a local model is used. |
| Companion integration | Remote HTTPS integrations fit naturally. Local processes require an installed helper or extension; ordinary browser code cannot launch a stdio MCP subprocess. | A companion helper can launch approved local processes or reach remote services, subject to explicit permissions and narrow capabilities. |
| Operations | Static asset delivery plus an optional small authenticated AI relay can avoid hosting a game simulation per player. Model requests and downloads still have costs. | Local simulation similarly avoids per-player simulation hosting. Installer distribution, updates and optional AI services remain operational work. |

**Verified Godot web constraints.** Current Godot 4 web export uses WebAssembly and WebGL 2 with Compatibility rendering; Forward+, Mobile and WebGPU are unavailable on that export path. Single-threaded export is supported; threaded export requires cross-origin isolation and appropriate hosting headers. Godot web networking exposes HTTP, WebSocket client and WebRTC rather than ordinary low-level native sockets. Background tabs can pause processing. PWA caching can enable offline loading after an initial visit. Test these behaviors on the selected engine patch. [Godot web export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

**GPU access and limits.** WebGPU provides rendering and compute capabilities, but is a separate backend choice rather than an automatic upgrade to a Godot export. Detect a usable adapter, required features and limits on the actual browser/OS/device; provide a clear unsupported path or separately built fallback. W3C specifies device limits and feature negotiation, while MDN still marks WebGPU as limited availability and requiring a secure context. WebGL does not expose a portable total-VRAM query, so choose a conservative asset budget and test allocation failure/context recovery rather than filling an inferred amount of free memory. [W3C WebGPU specification](https://www.w3.org/TR/webgpu/), [Mozilla WebGPU documentation](https://developer.mozilla.org/en-US/docs/Web/API/WebGPU_API), [Mozilla WebGL resource guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)

**Save durability.** Browser storage is generally best-effort unless persistence is granted; quotas and eviction policies differ. IndexedDB/OPFS and caches are origin-scoped, and private browsing commonly deletes stored data when the private session ends. Implement save export/import, quota-error handling and an explicit persistence check. Separate replaceable terrain caches from irreplaceable player changes. Changing the hosting origin needs a save migration plan. A PWA installation or successful write is not proof that a save is backed up. [Mozilla storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

**Remote streaming is a third product option.** With streaming, a remote computer simulates and renders the world, encodes video/audio, and receives the player's input. This can expose richer native graphics to a weaker client, but adds network travel, encoding/decoding, connectivity dependence and remote GPU/egress costs. These latency and cost implications are architectural inferences, not measured EnFractal results. Price concurrent sessions and actual player-hours before considering it within the early service budget. Streaming must not be described as the same inexpensive deployment as a locally executing web build. Epic's Pixel Streaming documentation illustrates this architecture; citing it does not propose adopting Unreal. [Pixel Streaming overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-pixel-streaming-in-unreal-engine)

## Engine and language choices

| Candidate | What it enables | Cost or unresolved question | Evidence needed |
|---|---|---|---|
| Godot + current GDScript/shaders | Preserves current gameplay, scene/editor tools and the direct web/native comparison. | High-volume procedural work, asset residency and the desired art must be measured; an engine export is not a complete browser product. | One representative scene and identical command workload in native and web builds. |
| Godot + C# | A conventional typed domain library and .NET tooling may improve maintenance for a larger rules system. | Current Godot 4 C# projects cannot export to web. Conversion adds build/interoperability work; a speed improvement is unproven. | A specific maintainability or CPU bottleneck, plus an explicit platform decision or a deliberately separate C# service. |
| Rust + Bevy | Open-source ECS, custom materials/render pipelines and native/WebAssembly paths; greater control for specialized engine work. | Existing Godot scenes, shaders and integration code need replacement. Tooling, physics integration, saves and companion plumbing still need evaluation. | A bounded native/web reproduction of the same scene and selected operations, including workflow effort. |
| Custom renderer/engine components | Can implement a visual or procedural technique a stock path cannot express adequately. | Rendering, asset tools, platform integration, debugging and long-term maintenance become project responsibilities. | An isolated, measured limitation and a small demonstrator that solves it without assuming a full rewrite. |

Godot's C# platform restriction is current, not a general claim that C# cannot run in browsers. A separate C# HTTP service can serve a web client, but moving the local simulation there would change offline behavior and operating costs. Python remains useful for offline geodata conversion, validation and asset preparation. Add Rust/C++ native code only for a specific measured need and account for a separate WebAssembly build where browser support is required. [Godot C# platform support](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/index.html)

Godot is MIT-licensed. Bevy offers MIT/Apache-2.0 licensing and extensible rendering, but its migration policy still describes an experimentation phase with breaking releases. Its official examples document separate WebGL2 and WebGPU builds; enabling WebGPU overrides WebGL2 and does not make the resulting build work on a browser without WebGPU. Pin the exact stable engine/toolchain used by each experiment and use examples from that version. Examples demonstrate available paths, not parity of every native feature on web. [Godot license](https://godotengine.org/license/), [Bevy features/license](https://bevy.org/), [Bevy migration policy](https://bevy.org/learn/migration-guides/introduction/), [Bevy release examples and web build instructions](https://raw.githubusercontent.com/bevyengine/bevy/latest/examples/README.md)

**Tiny Glade is a visual and interaction reference, not an engine preset.** Pounce Light says its game is written in Rust, uses Bevy's ECS/scheduling and other components, and has in-house rendering technology. It is not evidence that stock Bevy recreates its lighting, geometry behavior or performance. Likewise, choosing Rust does not produce its art direction. Evaluate soft forms, coherent palettes, lighting, readable depth, procedural joins and satisfying creation feedback on their own merits. Reproducing a particular rendering technique is a separate scope decision. [Tiny Glade developer technical notes](https://pouncelight.games/tiny-glade/info/)

## Connecting the player's AI

Separate three identities: the **player's local world/profile**, the **provider account used for inference**, and any **external agent authorized to call world tools**. An authenticated model response does not automatically have permission to change a world. Provider credentials are not world capabilities, and an MCP world token is not a provider credential.

The active default is an external player-owned agent in a dedicated game-only profile, connected through a paired local helper or authenticated bridge. The provider-hosting options below are alternatives, not prerequisites. A companion can also be driven by ordinary provider tool/function calls into a versioned game command API. MCP is an interoperability adapter for connecting an external agent or selected services; it is not a prerequisite for the embodied companion, a renderer, or the shared physics definition. Put provider-specific request formatting behind a small adapter so changing providers does not rewrite the simulation.

| Routing option | Credential location and path | Tradeoff / condition |
|---|---|---|
| Operator-funded companion relay (deferred alternative) | Browser/native client authenticates to EnFractal; relay calls an approved provider. Operator credentials stay server-side. | Requires a new product decision: the confirmed initial route is the player's own AI. Operator inference funding and provider-facing data custody are not prerequisites for this single-player plan. |
| BYO provider through a trusted relay | Player deliberately connects an eligible provider account, or supplies a key to a service they trust; relay stores/uses it separately from world data. | EnFractal becomes a credential custodian if it runs the relay. Requires secure storage, deletion/revocation, endpoint validation and clear disclosure. Prefer provider-supported delegated authorization when available. |
| Native client or installed local helper | Player's key/local model stays on their machine; helper sends only bounded results or actions to the game. | Strong local ownership and possible offline inference, with installation and resource costs. A local model competes with the game for RAM/GPU; benchmark the combined workload. |
| External player-owned agent | Agent keeps its own provider credentials and connects to narrowly scoped EnFractal world tools. Browser game uses an authenticated relay or explicitly paired local helper to receive accepted actions. | Keeps provider choice outside the game; setup and embodied responsiveness must be demonstrated. A remote agent cannot reach a browser tab's local state without an actual bridge. |
| Browser directly to provider | Only a provider-supported public-client/delegated or short-lived scoped credential flow, where offered and compatible with browser networking. | Verify each provider. Do not ship a long-lived secret in page code or make browser-stored API keys the default design. |

Do not assume every provider offers third-party OAuth, that one provider's token flow applies to another, or that an existing consumer subscription includes API access. Verify supported authentication, permitted use, model capabilities, data handling and billing at integration time. API keys must never enter save files, asset metadata, prompts, tool outputs or ordinary logs. A native binary cannot safely hide an operator-wide embedded secret either. Anthropic's own TypeScript SDK disables browser use by default because of secret-credential exposure; this is concrete evidence for keeping long-lived provider keys outside the page. [Official Anthropic SDK runtime guidance](https://github.com/anthropics/anthropic-sdk-typescript)

An ordinary browser page cannot launch a local stdio MCP server: that transport requires a client-launched subprocess. An installed application/helper or extension with native messaging can provide that boundary. Chrome documents native messaging as an extension-to-registered-host facility, not a normal webpage API. Remote MCP uses HTTP and requires compatible browser access/authentication. This browser/subprocess conclusion follows from those documented interfaces. [MCP transport definitions, revision 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports), [Chrome native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

For an installed local HTTP helper, bind to loopback, validate the requesting origin, authenticate each connection and pair deliberately with the player; localhost alone is not authorization. Test CORS, secure-context and browser local-network permission behavior in the actual deployment. For remote MCP, use audience-bound tokens and least privilege; never forward a token intended for one resource to another. MCP authorization authenticates access to the tool endpoint, while the world validator still checks each action and protection boundary. Pin protocol and SDK versions together: the current MCP revision changes transport behavior from earlier examples. [MCP HTTP security requirements](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [MCP authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

## Bounded experiments before a rewrite

Run these in an isolated experiment branch after coordinating with the active laptop work. Preserve the current playable implementation and reuse licensed source assets, a fixed seed, camera route, command fixtures and rule-version manifest. Implementation is future work; this document does not claim these experiments ran.

1. **Define the shared specimen: at most 4 owner-hours.** Use one small real-data terrain patch, a water boundary, a castle/structure, vegetation/mushrooms, an avatar and a visibly embodied companion. Include traversal at the 0.30 m player scale across representative curb/root/deck geometry, a simple rideable-creature proxy, one bounded wind/water action, one protected object and save/undo. Use recorded companion command fixtures for reproducible engine measurements. Visual prototypes can stand in for unfinished generation, but label them. This is not a promise to complete every fantasy system inside the experiment.
2. **Godot native/web comparison: at most 12 owner-hours.** Export the existing GDScript specimen to native and web Compatibility. Start with the simplest web export; try threaded web export only when a measured need justifies its deployment constraints. Measure both on the same machine, then run the attainable browser/device matrix. A native Mobile/Forward+ visual variant may be an additional comparison; clearly label its feature differences.
3. **Bevy native/web challenger: at most 12 owner-hours.** Reproduce only the specimen's decisive subset using stable Bevy, with WebGL2 and WebGPU builds where supported. Retain the same geometry, texture sizes, view, action scope and rule outcomes. Record missing features and integration effort instead of substituting a much simpler scene and declaring victory. Do not replace the main game or build a custom renderer during this cap.
4. **Companion connection, recovery and decision: at most 8 owner-hours combined.** Demonstrate one real player-owned agent connection in the viable candidate(s), an embodied response, cancellation, an invalid/over-budget command, a protected-area attempt, provider failure and save/reload. Test a browser relay plus a native/local route only to the depth necessary to settle the integration decision. Use a fixed request/spend allowance chosen before running; do not expose real keys in captures. Recorded fixtures remain the performance baseline because model responses vary. Reserve part of this same eight-hour allowance for the comparison report and platform decision; it is not an additional budget.

The caps total at most 36 owner-hours across stages, excluding unavailable test hardware or separately approved extensions. Stop each stage at its cap and record incomplete work as uncertainty. An inability to assemble a fair Bevy comparison within the cap is information about current development cost, not proof of a runtime performance ceiling.

Record the following evidence for each tested configuration:

- Exact commit, engine/toolchain, OS, browser, GPU, renderer, resolution and quality settings; identify any unavailable target device.
- Cold download/start time, warm restart, payload size, frame-time distribution, simulation-step distribution and input response during the same route/actions. Use a simple empty scene only to understand baseline overhead.
- Available CPU/browser-process/GPU memory measurements with their accounting limits; asset allocation estimates, peak creation load, residency after repeated create/delete/undo, and cache growth. Do not report disk cache as RAM or equate WebGPU buffer limits with total VRAM.
- Side-by-side captures judged for painterly forms, lighting, depth, procedural joins, effect readability and companion presence. Record lost techniques as well as successful approximations.
- Save/export/import/recovery, quota or disk failure, tab suspension/resume, GPU loss where testable, provider disconnection and cancellation. Check that recovered state has the same protected objects and accepted action results.
- Time to implement, debug, build and distribute a small change on both machines; source/data reuse versus actual rewrites.

Before measurements begin, choose provisional acceptance thresholds for startup, frame pacing, memory, action scale and supported devices. The earlier 720p/30 fps and 8 GiB integrated-graphics aspiration can inform that discussion, but are not established capabilities. A powerful discrete-GPU laptop or a RAM limit imposed on it does not validate a low-end integrated GPU.

## How to decide from the evidence

Choose **browser-led delivery** if the locally running browser version preserves the core companion/creation experience, desired appearance and save recovery on the agreed device matrix. Choose **native-led delivery** if a documented browser constraint removes a core experience and the installation cost is acceptable. Choose **both** only if shared code/assets and validation effort make that sustainable; a browser demo can be a separate scope with clearly described limits. A Bevy migration requires evidence that its benefit outweighs replacing working systems. A custom renderer requires a specific visual/technical need and its own bounded proof.

If neither route meets the creative requirement, revisit representation, active-world size and target-device choices before escalating to a full engine rewrite. If the only working browser route is remote streaming, make its ongoing cost and latency a separate product decision. Keep multiplayer deferred throughout this gate; portable commands, versioned saves and explicit rules preserve useful options without requiring a shared server now.
