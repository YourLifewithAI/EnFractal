# Performance, rendering, language and engine plan

> **Current direction — 2 October 2026:** The [revised roadmap](../ROADMAP.md) and [backlog](../BACKLOG.md) govern scope and order: single-player embodied AI first, multiplayer last. Native Godot .NET with C# is now selected in the [accepted ADR](../../engine/decisions/0001-native-godot-csharp.md). Existing GDScript migrates incrementally; shaders and Python remain. Alternative engine/browser experiments in [study 14](14-single-player-platform-and-engine.md) are deferred. The dated research below is retained for context.

Planning date and primary-source lookup: 2026-09-30. This document proposes decisions and acceptance targets; it reports no game benchmarks. Implementation remains unauthorized in this planning phase.

## Recommendation and decision boundary

Start with **Godot .NET and C#**, targeting a native Windows client and a Linux headless authoritative host. Prefer the Compatibility renderer for the minimum specification; compare Mobile on supported hardware. Keep one C# rules library independent of Godot scene objects. Use GDScript sparingly for presentation helpers, Godot's shader language for graphics, JSON Schema for interchange contracts, and SQL for persistence. A TypeScript MCP adapter may run beside the host if it materially simplifies its supported SDK integration. It must not run simulation or duplicate rule enforcement.

This is a recommendation about the smallest maintainable system for one person assisted by coding agents, with hosting and AI below $100/month. It is not a claim that C# is the fastest language or that Godot already supplies a planetary multiplayer game. Godot's MIT license supports the copyable-code objective; its documented .NET desktop support and dedicated-server exports fit this native-first plan. Current stable documentation says C# projects cannot export to the web. Browser gameplay therefore requires a separate decision, not an unchecked export box. [Godot license](https://godotengine.org/license/), [C# platforms](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/index.html), [server export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html).

Pin an actual stable engine patch, .NET SDK and dependencies when implementation starts. Record versions in the architecture decision. Avoid development branches, a custom double-precision engine build, several server languages, Kubernetes and a homemade renderer in the MVP. One host may contain a home-world process, one sleeping/on-demand sandbox process, a small gateway/adapter and one database. These are local deployment units with explicit interfaces, not a distributed microservice program.

The decisive uncertainty is whether the chosen engine supports the intended movement, editable world and art on the target devices while remaining manageable. The capped initial spike below checks basic feasibility before substantial content is made; the later integrated slice validates persistence, portals and multiplayer performance.

## Engine and language deliberation

The judgments below are engineering assessments, not benchmark rankings. Separate **runtime efficiency** (CPU, GPU, memory and network use), **development efficiency** (debugging, iteration and tooling), and **operational robustness** (recoverability, upgrades and predictable resource limits).

| Candidate | Strengths for this project | Main constraints and effort | Position |
|---|---|---|---|
| Godot + C#, limited GDScript | Editable engine source; conventional managed code and reusable domain libraries; scene tools; native/headless build path; controllable simple rendering | C# allocations and managed/native crossings need profiling; custom geographic streaming; multiplayer persistence and security remain our work; no supported C# web export | Provisional choice |
| Godot + primarily GDScript | Short editor iteration; fewer language/tool integrations; attractive if browser export becomes essential | Dynamic logic and high-volume loops require care; backend library reuse less convenient; moving every node into scripts will not solve object-count costs | Valid simplification if C# maintenance dominates |
| Unity + C# / URP | Mature content tooling, profiler and extensive ecosystem; dedicated-server optimizations; Burst offers native compilation for a restricted high-performance C# subset | Proprietary engine; licensing/seat eligibility; packages and asset licenses; patch/version coupling; still requires authoritative world architecture | One challenger, only if needed |
| Unreal + C++ / Blueprints | Strong terrain tools, World Partition, large-world facilities and built-in network foundations | Larger content/build/tooling surface for this team; low-end quality requires careful configuration; engine source available under EULA rather than a permissive open-source license | Defer unless requirements change |
| Rust + Bevy | Memory safety and explicit ownership; ECS/data-oriented control; permissively licensed; selective engine features | More assembly of editor, networking, persistence and creator tooling; Rust expertise and migration burden; no automatic low-end performance victory | Specialist future path, not first MVP |
| TypeScript + Babylon.js or Three.js | Shareable browser entry, web UI integration; inspectable open code; TypeScript can share control-plane types | Browser graphics/memory/context-loss constraints; transport differences; server still necessary; Three.js is primarily a graphics library, requiring more game systems | Atlas/editor preview later; alternative if browser entry becomes mandatory |
| Luanti C++ engine + Lua game/mod layer | Existing open voxel platform, game creation, server workflows and mod ecosystem can substantially shorten a block-building prototype | Voxel-world assumptions conflict with freely shaped creatures, curved Earth and general rigid-body invention; deep modifications risk maintaining an engine fork | Serious fallback if product accepts block worlds |

Unity documents GPU-asset stripping for dedicated servers and Burst compilation. Its current product page still ties free Personal eligibility to the $200,000 annual revenue/funding threshold; pricing and terms must be rechecked at commitment, and an old runtime-fee announcement must not be used as current cost. [Unity server optimizations](https://docs.unity3d.com/6000.0/Documentation/Manual/dedicated-server-optimizations.html), [Burst](https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/index.html), [Unity plans](https://unity.com/products).

Unreal's World Partition streams grid cells; it does not allocate ownership across authoritative servers. Its documented large-world coordinates improve numerical precision, not RAM capacity. The published game model generally applies a 5% royalty above the first $1 million of lifetime product revenue, subject to applicable exclusions/discounts and the actual EULA. This is relevant to long-term business comparison, not a reason to optimize this tiny prototype around hypothetical revenue. [World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine), [large-world coordinates](https://dev.epicgames.com/documentation/unreal-engine/large-world-coordinates-in-unreal-engine-5), [Epic royalty explanation](https://www.unrealengine.com/news/unreal-engines-improved-royalty-reporting-system).

Bevy offers MIT/Apache-2.0 licensing, but its own migration documentation describes breaking releases during its experimentation phase. That increases maintenance risk for an inexperienced solo integrator; Rust cannot remove that cost. Luanti's source repository identifies its voxel focus and LGPL licensing; game assets and mods need their own license review. [Bevy source/license](https://github.com/bevyengine/bevy), [Bevy migration policy](https://bevy.org/learn/migration-guides/introduction/), [Luanti source](https://github.com/luanti-org/luanti).

Babylon lists a broad engine feature set; Three.js is MIT-licensed and Babylon Apache-2.0. Browser deployment does not make graphics resources free: Three.js explicitly requires disposal of obsolete geometry, materials and textures. Use the same bounded cache discipline regardless of language. [Babylon features](https://www.babylonjs.com/specifications/), [Babylon license](https://github.com/BabylonJS/Babylon.js/blob/master/license.md), [Three.js license](https://github.com/mrdoob/three.js/blob/dev/LICENSE), [Three.js disposal](https://threejs.org/manual/pages/how-to-dispose-of-objects.html).

Geospatial integration is another tradeoff. Cesium Native documents official Unity/Unreal integrations and a community Godot integration; the latter must be evaluated for maintenance and licensing. A Godot choice therefore includes a terrain-integration risk. For the first small region, preprocessed licensed terrain tiles and a simple manifest are more bounded than introducing a general geospatial plugin stack. [Cesium Native integrations](https://cesium.com/learn/cesium-native/ref-doc/index.html).

C++ or Rust native hot paths are a later escape hatch for measured bottlenecks such as mesh generation, not an initial third implementation of the rules. Require a profiler capture, equivalent output tests and at least a meaningful improvement in whole-frame/tick time before accepting native complexity. C# does not make collision detection managed: the engine's native physics implementation still performs that work. Shaders are a separate language; JSON is data; MCP is a protocol. Art styles generally do not require a particular application language.

## Hardware targets and measurable envelopes

The observed planning machine has an i7-10875H (8 cores/16 threads), 31.79 GiB RAM and RTX 2070 Super; the root hardware query subsequently confirmed **8192 MiB dedicated VRAM** with `nvidia-smi`. It also exposes Intel UHD graphics. No measurements establish which adapter the game will use or its sustained performance. The 8 GiB iGPU target is a separate minimum-device hypothesis; restricting RAM on the current machine is useful stress testing but does not reproduce another GPU, driver or memory bandwidth.

All following values are proposed gates to validate, not published requirements or capacity claims.

| Budget | Minimum profile | Observed-machine target |
|---|---|---|
| Resolution and frame pacing | 1280×720, capped 30 fps; warm p95 frame ≤33.3 ms, p99 ≤50 ms | 1920×1080, 60 fps; p95 ≤16.7 ms, p99 ≤25 ms; optional 30 fps thermal mode |
| Memory | ≤2.5 GiB total attributable CPU/shared-GPU allocation envelope; preserve OS headroom | ≤4 GiB client private working set; ≤2 GiB GPU allocations initially |
| Geometry diagnostic envelope | 250,000 visible triangles and 350 draw calls including extra passes | 750,000 triangles and 700 draws initially; only increase after measurements |
| Terrain/asset staging | ≤128 MiB decoded staging; two background decode jobs | ≤256 MiB staging; two jobs initially |
| Main-thread streaming work | ≤2 ms per frame; defer expensive work | ≤1 ms per frame initially |
| Texture policy | 512 px common assets, 1024 px selected hero assets; shared atlas/materials | 1024 px common, selective 2048 px heroes |
| Disk cache | 2 GiB default, bounded and clearable | Same default; optional larger cap |
| Streaming transfers | 256 KiB/s default per client while playing; configurable | Same; first install separate and clearly sized |

GPU and CPU timing overlap: do not add independently measured GPU time to CPU wall time and call the result a frame. Measure both, plus presented frame intervals. Shared graphics memory accounting can double-count mappings; record process commit/private working set and shared GPU attribution separately before claiming the 2.5 GiB gate passes. Report resident and committed memory. Cache size is disk usage, not permission to retain that much RAM.

On a candidate 8 GB-class host, measure actual usable memory rather than treating GB and GiB as interchangeable. Start with ceilings of 3 GiB combined for simulations and 1 GiB for database/gateway/adapter, adapt OS/file-cache allocation to actual bytes, and preserve at least 2 GiB safety margin by reducing other ceilings if needed. These are allocations to validate, not guaranteed consumption. Initially cap **eight connected participants across home Earth plus one active sandbox**, with at most four in that sandbox. Empty sandboxes sleep. Home persistence does not imply that every location runs continuous physics. RAM capacity does not promise a dedicated CPU; record the selected plan's CPU entitlement, contention and tick jitter before promising capacity. The canonical [business budget](07-business-costs-and-reinvestment.md) allocates $55 to the host and $15 reserve within a $95 total. Sleeping a process frees capacity but does not reduce a fixed VPS bill.

## How an Earth fits within those limits

Maintain a global geographic address independently of active scene coordinates: world ID, region ID, geographic anchor, local position and coordinate-frame version. Use doubles for geographic transforms/metadata and bounded local float physics frames. A low-detail globe/atlas supplies context; only visited, prepared regions become detailed playable scenes. Never allocate Earth-sized arrays or retain every tile manifest entry as a heavyweight scene object.

Godot's large-world documentation warns about extra memory/performance costs and custom recompilation for double precision, including extension compatibility concerns. Prefer ordinary builds plus local frames until a concrete precision test proves them insufficient. The map team owns geographic correctness; the physics team owns handoff and local-frame invariants. [Godot large worlds](https://docs.godotengine.org/en/stable/tutorials/physics/large_world_coordinates.html).

Terrain passes through a bounded pipeline: choose visible tile LODs by screen error; prioritize nearby collision and visible coarse terrain; read cached compressed assets; decode off-thread; upload a limited batch; replace LOD atomically; evict unused decoded/GPU resources. Include hysteresis to avoid LOD thrashing and skirts or verified shared edges to hide cracks. Limit outstanding requests, decompressed size, triangle count and material count before allocating. Cancel stale work after a portal jump. Keep coarse coverage visible while detail loads; block entry onto missing authoritative collision with an understandable loading boundary.

Start with 64–128 m render patches inside a small kilometer-scale test region, treating the final patch size as a measured choice. Static distant terrain is visual only; near interaction geometry comes from the authoritative map version. Merge repeated static props, use per-patch instancing for vegetation and progressively coarser silhouettes. Avoid one node per blade of grass, terrain sample or decorative rock. Godot offers lower-level rendering/physics server APIs if node management becomes a measured bottleneck. [Godot server APIs](https://docs.godotengine.org/en/stable/tutorials/performance/using_servers.html).

The low profile uses one simple sun, limited or disabled real-time shadows, ambient lighting, opaque materials and distance fog. It requires no ray tracing, volumetric clouds, screen-space reflections, compute shaders or dynamic global illumination. Common effect volumes get simple visible silhouettes so reducing particles never hides gameplay. Only four nearby avatars need full animation updates at first; others use reduced animation cadence while authoritative locations and accessible identity cues remain current. Portals show a thumbnail or bounded static preview; no recursive live-world rendering in the MVP. Godot documents Compatibility as its widest-hardware renderer and explains feature differences; fallback visuals must be deliberately authored and checked. [Renderer comparison](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html).

Resource pressure policy: shrink cosmetic distance first, reduce effects/shadows next, reduce render scale last. Preserve readable telegraphs, collision and action permissions. At a hard allocation threshold, stop accepting new cosmetic assets, unload safely and show a plain placeholder. Reject oversized user creations at publication and again at loading. A paid tier cannot bypass the client safety ceiling.

## Network and simulation budgets

Begin with fixed **30 Hz authoritative simulation**, 15 Hz nearby snapshots and interpolation on remote entities. Benchmark 60 Hz physics with 30 Hz commands if gliding/contact behavior fails at 30 Hz; changing this consumes server headroom. Each snapshot carries a simulation tick and world/frame version. Client prediction is limited to supported local movement and reconciles to server outcomes; do not require cross-machine deterministic rigid-body lockstep.

Godot provides ENet, WebRTC and WebSocket implementations; native ENet is a reasonable initial transport. Browser transport constraints and engine RPC behavior mean the long-term open-world protocol should be versioned message schemas rather than saved scene-tree paths. Use separate traffic classes for inputs, snapshots and reliable transactions. Transport alone does not authenticate an account or make a command authorized. Select and review encryption/authentication before exposing a server. [Godot networking](https://docs.godotengine.org/en/stable/tutorials/networking/high_level_multiplayer.html).

Start with the physics team's region allowances: 128 awake rigid props, 32 joints and 16 active effect volumes, with aggregate home-plus-sandbox work limits. These are stress-scene sizes, not promises to every player simultaneously. Aim for p95 server tick work ≤20 ms and p99 ≤30 ms at 30 Hz, leaving headroom inside 33.3 ms. Bound total event processing and spread persistence/serialization work outside the tick. After overload, stop new expensive creations, explain the reason, and retain existing valid state; never allow unbounded catch-up loops or silently weaken permission checks.

Interest management sends only permitted, relevant objects. Near entities get frequent deltas; distant visible landmarks get cheap summaries. Static assets travel by hash and cache; reliably persisted edits travel as transactions. Rendering range, replication range, simulation activation and land ownership remain separate. Eight colocated inventors are a required worst-case test, not equivalent to eight quiet explorers.

Target per-player gameplay egress average ≤30 KiB/s and p95 ≤60 KiB/s over 60-second windows; input traffic ≤8 KiB/s. Tile transfers use HTTP separately, with four host-wide concurrent downloads initially and a monthly byte budget. Eight continuously active clients at 30 KiB/s consume approximately **637 GB/month** before assets and overhead. Budget actual player-hours and provider transfer limits. A 100 KiB/s bandwidth figure is not “small” when multiplied across persistent sessions. AI requests never occur per frame or per tick; manual creation and play remain available when the AI budget is exhausted.

## Initial stack spike and later integrated evidence

Spend at most approximately **20 owner-hours** on the first stack decision gate, with agents preparing minimal fixtures independently. Stage A covers a native client build, a headless build, a small terrain patch with a capsule controller, and representative static meshes/rigid props. Capture empty-baseline and stress-scene timing, memory and build/iteration effort. This is a feasibility spike, not a completed game: networking, saved worlds, safe portals, AI creation and full streaming are not prerequisites for this gate.

Initial hard gates: native/headless builds run; the owner can modify and debug the capsule scene; chosen dependencies and licenses fit copying and native platforms; representative simple rendering/physics shows no critical compatibility, memory or performance blocker. Select Godot provisionally when those pass. Reserve a further **8–12 owner-hours** for a Unity challenger only if Stage A exposes an attributable engine blocker that scope reduction cannot reasonably resolve. Reuse identical meshes, textures, collision shapes, camera route and entity counts. These are workload allowances, not calendar guarantees. If the allowance expires, record what was measured, unresolved risks and the next narrow experiment; do not pretend the entire stack has been certified. If both candidates fail, reduce scope or investigate the Luanti product variant before constructing a custom engine.

The **later integrated-slice gate**, after its dependent features exist, adds walking a terrain seam, fast gliding through streamed terrain, eight networked avatars, maximum allowed props/effects, portal entry/return, save/reconnect and repeated asset churn. It requires recoverable save/return, bounded memory, the low-profile frame gate, acceptable movement and correct shared outcomes. This gate belongs to the multiplayer/persistence milestones and has its own schedule; its full implementation is not included in the initial 20 hours.

For both stages, keep settings and fixtures reproducible. For integrated tests, include cold-cache and warm-cache runs; repeat three times after a ten-minute warmup. Preserve raw logs, build version, adapter, resolution, power mode and background processes. Record p50/p95/p99 frames/ticks, >100 ms hitches, peak/settled memory, allocation/GC stalls, GPU load, network bytes and preparation effort. Evaluate maintainability/owner debugging 30%, minimum-device performance 25%, authoritative networking/persistence fit 20%, creation workflow 15%, geographic integration 10%. Early entries without implementation evidence remain explicitly unscored; mature scores are populated at the integrated gate.

Integrated two-hour soak: loop exploration, 100 portal round trips and creation deletion; no crash, GPU reset, runaway thread/request count or steady memory growth. After caches reach their caps, settled memory should return within 10% of the established baseline and trend under 20 MiB/hour; investigate deviations rather than hiding them with forced collection. Test disk-full, corrupt tile, interrupted download and memory pressure. Record temperature/clock trends and sustained frames under ordinary manufacturer settings; never disable protection or require overclocking. Later run an overnight server soak and a real remote playtest at 50/100/200 ms RTT, 1–3% loss and constrained bandwidth. The game must fail gracefully and retain ownership even when movement quality degrades.

## Parallel agent packets and dependencies

These are roles that can be scheduled in small waves, not a recommendation to pay for every role continuously. One owner/integrator merges and reproduces results. Independent review belongs to a different agent from the implementation.

| Packet | Inputs and responsibility | Reviewable output / acceptance |
|---|---|---|
| S1: stack and licensing | Requirements, platform assumption, existing skill level | Versioned decision record, dependency/license inventory, native/headless feasibility checklist; no unexplained engine fork |
| S2: matched harness | S1 candidate; physics stress fixtures; art fixture | Deterministic camera/input replay and metrics specification; tests do not privilege one candidate's visual quality |
| R1: terrain residency | Map manifest, coordinate contract, authoritative collision versions | Request/cancel/evict state diagram; seam and portal-loading tests; bounded queues and decoded allocations |
| R2: asset/performance policy | Art selection and minimum profile | Asset validator limits, shared materials/LOD rules, shader fallback matrix; effect meaning visible at every setting |
| N1: replication budget | Entity schemas and permission visibility | Message/version contract, byte-cost worksheet, loss/reorder scenarios; same outcome regardless of graphics setting |
| O1: host resource envelope | Persistence/portal plan and monthly budget | Whole-host memory/CPU/egress plan; sandbox admission/sleep policy; restore/load tested inside caps |
| Q1: independent performance review | Release binaries and harness results | Reproduced logs and adversarial stress findings; no capacity claim based only on average fps |

R1/R2/N1 can proceed in parallel after contract freeze. S2 needs only fixture contracts, not finished art. O1 can plan alongside them. Q1 starts after a reproducible build exists; it must not rewrite pass thresholds after observing a failure. Each packet should be small enough for one coherent change/review, with an explicit stop condition and context bundle. Agent time does not replace the owner's playtesting or responsibility for understanding changes.

Open decisions: actual minimum-device access; native-only acceptance; owner's willingness to maintain C# tooling; required avatar scales/speeds; maximum editable terrain area; hosting CPU performance and transfer allowance. None blocks planning. Before implementation, resolve platform and maintainability choices, then use measurements to replace these provisional envelopes. Preserve the small shared-region experience when cutting scope; a smooth globe flyover alone does not validate invention, shared consequences or safe portals.
